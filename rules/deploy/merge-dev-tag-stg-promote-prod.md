# Deployment Strategy (Merge → Dev, Tag → Stg, Promote → Prod)

dev / stg / prod の3環境を持ち、マージで dev、タグで stg へ自動デプロイし、prod へは検証済みのタグを人が昇格させる戦略。

## 概要

`main` へのマージで dev に自動デプロイして継続的に統合検証し、タグを打って stg へ自動デプロイして実機検証する。prod へは、検証を通したタグを指定してパイプラインを人が実行し、同一成果物を昇格させる。dev と stg を自動で回しつつ、本番反映のタイミングだけを人が握りたいリポで採用する。

## 環境とトリガー

| 環境 | トリガー |
|---|---|
| dev | `main` へのマージ → 自動デプロイ |
| stg | タグ (`vX.Y.Z`) push → 自動デプロイ |
| prod | パイプラインの手動実行 (`workflow_dispatch`) でタグを指定 → デプロイ |

## ゲート

prod へのパイプライン実行が手動ゲート。dev で統合検証し、stg で実機検証したタグを人が選んで昇格させる。

## 反映方式

CI がマージを起点に成果物をビルドし、以降の環境ではビルドせず同一成果物を昇格させる。prod への昇格は、指定されたタグが指すコミットの成果物を対象とする。

## タグ・バージョニング

SemVer 形式のタグ (`vX.Y.Z`) を人が手動で打つ。タグを打つ行為が stg への反映を意味する。

## ロールアウト

ローリング更新。詳細はデプロイ先のサービスに従う。

## 想定リポ / 選定の目安

- コンテナ / PaaS 上で稼働し、コミット単位に環境を切り替えられるアプリ
- stg での実機検証を挟みたいが、prod 反映のタイミングは人が決めたいもの
- stg が不要なら `merge-dev-tag-prod.md`、全環境を人が反映するなら `manual-pipeline.md` を検討する
