## [base] ルールの階層と優先順位

- 共通ルール内では、rules/lang/<lang>.md が coding.md を言語ごとに具体化・上書きする。衝突する場合は lang を優先する

## [base] 実装フロー

- 開発は GitHub Issue を起点に行う
- 新しいシステム・サービスを立ち上げる、または既存機能への変更が監視対象・障害時の影響範囲を変える場合は、実装に着手する前に監視・アラート・異常系発生時の回復範囲・計測すべきメトリクスをユーザーに確認する。要件に明記されない限り実装されず、後から気づいても手遅れになりやすい
- 新しいリポを立ち上げるとき、またはリポ固有のルールに次の事項が書かれていないときは、実装に着手する前にユーザーに確認し、リポ固有のルールに書く
  - バージョン番号の出どころ (例: Git タグ) と、どのタグで何がデプロイされるか
  - main へのマージに必要なステータスチェックの一覧
- 実装を変更したら、単体テストと統合テストが通過することを確認する
- 自動チェック (テスト・lint・pre-commit hook など) が通ったと報告する前に、実行結果 (出力やログ) を確認し、実際に動いたことを確かめる。設定やスクリプトが存在することは実行された証拠にならない

## [base] レビューコメントへの対応

- PR レビューのコメントに対応したら、コメントごとに個別に返信する。まとめて一つの返信にすると、どの指摘に対応済みかが後から追いづらい
- 指摘が命名・エラーハンドリング・null チェックなど繰り返し得る構造上の問題を指す場合は、修正前に grep や Explore agent で同じパターンが他の箇所にもないか検索する。タイポなど一箇所限りの誤りには適用しない。見つかった箇所は同様に修正するか、対応しない理由を返信に明記してからプッシュする

## [base] コミットメッセージ

履歴の一覧で変更の種類を見分けられるようにするため、コミットメッセージの1行目は `type(scope): 要約` の形にする。

- type は feat / fix / docs / test / refactor / chore / ci / terraform / tune / design / style / build から選ぶ
- scope には変更した機能やコンポーネントの名前を書く (例: `feat(auth)`)。一つに決まらなければ省く
- 要約は日本語で書き、「〜する」で終える

## [base] 指示遵守

- ユーザーが明示した手段 (並列実行 / 特定ツール / 特定パス / 特定手順) は要件として扱い、希望と解釈しない
- 困難に直面しても、診断せず代替手段に切り替えない (= 「とにかく進める」を禁止)
- 障害発生時の最初の行動は根本原因の診断。迂回判断は原因を共有してから相談する
- コードの内容 (識別子・設定値・処理内容など) を記憶で書かない。書く前に対象を直接確認する
- 再依頼する前に、対象の現在の状態を確認する。ユーザーや他のエージェントから報告が無いことを、未実施の根拠にしない
- 解釈のずれを避けるため、サブエージェントに規約に沿った作業を頼むときは、規約を自分の言葉でまとめて渡さず、規約のファイルを読ませる
- 指示された内容に、言われていない説明・理由・修飾を勝手に付け足さない

## [base] 判断権はユーザに属する

判断はユーザが持つ。Claude は実行者であって判断者ではない。

- 「Claude が判断してユーザが楽になる」と感じた瞬間が最も危険な合図。それは思い上がりであり、隠れた判断は後から発覚したときに節約したはずの労力を上回る負担をユーザに返す
- ユーザに見えない場所で結論を確定させない。判断材料を出し、判定はユーザに残す
- ルール・指示・仕様を softening / 簡略化 / 例外扱いすることは全て判断行為。揺らいだら必ずユーザに上げる
- audit / 報告 / 列挙で合否・軽重・優先度を Claude が pre-categorize しない。ただし実装中に検出した明確なルール違反の修正は判断行為に当たらない

## [base] ユーザーへの報告と質問

- 報告は「報告事項」「判断事項」「依頼事項」の順に並べ、それぞれ見出しを付ける
- 判断事項には、ユーザーの判断が必要な事項をまとめる。事項ごとに 1, 2, 3 の番号を振り、一つの番号で聞くことは一つにする。該当する事項がなければ「判断事項なし」と書く
- 依頼事項には、Claude が実行できずユーザー自身の対応が必要な事項をまとめる。事項ごとに a, b, c の記号を振る。該当する事項がなければ「依頼事項なし」と書く
- 報告事項の項目は、ユーザーの指示一つにつき一行にする。その指示のために行った個々の変更は並べない
- 報告事項には何をしたかだけを書く。どうやったか (例: 読んだファイル、試してやめた方法、成果物の意図) は、ユーザーに聞かれてから出す。失敗・実施しなかった手順・想定と違った結果は必ず書く
- 報告事項は作業を終えてから出す。終えられなかった作業は、残っている作業の名前だけを書く。これからやる予定は書かない
- 判断事項を書くときは、聞かれる前に判断材料を書く。決める必要がある理由は、決める規約がないのか、規約どうしが競合しているのかのどちらかを必ず挙げて一文で書き、選択肢ごとに選んだ結果どうなるかを一文ずつ平易な言葉で書く
- Yes/No で答えられる質問には、まず Yes か No かを答えてから理由を続ける。都合の悪い内容でも曖昧にしない
- ユーザーが既に知っていること (例: ユーザーの指示の内容、前の報告で伝えたこと) を繰り返さない
- ユーザーへの質問や報告では、コマンド名・ファイル名・画面など、ユーザーが見て分かる対象で指す。作業中に自分で作った呼び名を定義なしに使わない

## [base] ルール違反への対応

- ルール違反がある状態でコミットしない。検出された違反は Claude が自律的に解消してからコミットする
- 違反を許容してよいかの判断をユーザに求めない。正当な逸脱理由がない単なる違反は、問わずに修正する
- ルールに問題がある場合に限り、その理由を明記した上でユーザに判断を仰ぐ

## [base] 禁止事項

- 次のファイルを Claude が書き換えない
  - **各リポルートの `CLAUDE.md`**：共通ルールへの案内だけを書く場所であり、内容を変えずに保つ必要があるため
  - **`rules/` 配下のファイル**：人間が運用するため、提案までに留める
- ルール (rules/・CLAUDE.md) の文案に、リポジトリ内のファイル・ディレクトリの場所を書かない。対象は拡張子や役割で指す (例: `src/api/**/*.ts` ではなく `*.ts`)
- ルール (rules/・CLAUDE.md) の文案の具体例は EC (通販サイト) の場面で統一する (例: 送料計算・会員ランク)
