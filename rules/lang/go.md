## [lang/go] 設計思想

- 保守性と拡張性を最大限に高めるため、クリーンアーキテクチャを遵守する
  - ビジネスロジックは外部アダプターに依存しない
  - 純粋な port や delivery 層とロジックを分離する
  - リポジトリ層は純粋な外部永続装置へのアクセスであり、ロジックを持たない
  - リポジトリ層は外部永続装置以外に依存しないため、API 契約の型を使わない

## [lang/go] テスト方針

- テストは標準 `testing` と `stretchr/testify` を用いる
- テストコードはテーブル駆動 (`t.Run` でケース分岐) で書く
  - 単一シナリオや前提条件が異なるテストは無理にテーブルにしない(1 行だけのテーブルを作らない)
- テストの命名は testing.md「テストの命名」を次のとおり割り当てる
  - テスト関数名 = `Test<対象>` (例: `TestShippingFee`)。Go がテスト関数と認識するのは `Test` で始まる関数名だけで、日本語にできない。仕様は日本語で書くため、テスト関数名は仕様ドキュメントに出さない
  - 大分類 = 関数の直下に置く `t.Run` の名前に日本語で書く (例: `t.Run("[注文]送料計算", ...)`)
  - 各ケースの名前 = その `t.Run` の中に置く、ケースごとの `t.Run` の名前 (テーブル駆動ならテーブルの name フィールド) に日本語で書く (例: `t.Run("注文金額が3000円のとき、送料は無料になる", ...)`)
  - 小分類 = 大分類とケースの `t.Run` の間のどこにでも重ねる `t.Run` の名前に日本語で書く
  - 正常異常 = 大分類とケースの `t.Run` の間のどこかに重ねる `t.Run` の名前に「正常系」「異常系」と書く
  - テーブル駆動で操作 (When) を書くときは小分類の `t.Run` に書き、テーブルの name フィールドには Given + Then を書く
  - `go test` は名前の半角空白を `_` に置き換えて出力するため、名前に半角空白を入れない。`[...]` の直後も詰めて書く (例: 「[注文] 送料計算」ではなく「[注文]送料計算」)
  - ケースが 1 つだけのときも、テーブルにはせずその 1 ケースを `t.Run` で書く
    - なぜ: 仕様ドキュメントに全テストがケース名の粒度で出力されるようにするため

## [lang/go] コード生成

- 型コードは REST 契約 (OpenAPI 定義) ・Pub/Sub 契約 (AsyncAPI 定義) を SSoT とし、型生成スクリプトで再生成する

## [lang/go] docs コメント

- docs コメントは godoc 形式で書く (識別子名で始める)

## [lang/go] 命名

- ctx / cfg / tx など Go で確立された短縮語は使ってよい
- コンストラクタは New<型> (パッケージの主要型が一つなら New)
  - functional option は With<項目>
- 型変換を関数で表す場合は To<型>
- 型変換をメソッドで表す場合は目的の型名にする
- getter は動詞を付けず対象名そのものにする
- レシーバ名は型を表す 1〜2 文字の短縮にする

## [lang/go] 分岐

- `switch` には必ず `default` 節を書き、想定外の値としてエラーを返す (または panic する)。空の `default` で無言に通過させない
