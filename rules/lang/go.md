## [lang/go] ディレクトリ構成

- `main` は `cmd` に置く。アプリの実装は `internal` に置く
- アーキテクチャ上の役割の名前は system-design.md「クリーンアーキテクチャと役割の名前」に従う。Go 固有の役割は次のとおり。使わないものは作らなくてよい
  - `presenter`: domain と外部に渡す形式との変換
- テストファイル (`_test.go`) は、対象ファイルと同じディレクトリに置く。複数のテストで共有する部品は、対象パッケージの下の `<パッケージ名>test` サブパッケージに置く

## [lang/go] テスト方針

- テストは標準 `testing` と `stretchr/testify` を用いる
- テストコードはテーブル駆動 (`t.Run` でケース分岐) で書く
  - 単一シナリオや前提条件が異なるテストは無理にテーブルにしない(1 行だけのテーブルを作らない)
- テストの命名は testing.md「テストの命名」を次のとおり割り当てる
  - テスト関数名 = `Test<テストする関数の名前>` (例: `TestShippingFee`)。Go がテスト関数と認識するのは `Test` で始まる関数名だけで、日本語にできない。仕様は日本語で書くため、テスト関数名はテストケースカタログに出さない
  - `[区分:大機能(:中機能)]小機能` = 関数の直下の `t.Run` の名前 (例: `t.Run("[本体:注文]送料計算", ...)`)
  - ケース = 小機能の `t.Run` の直下の `t.Run` (テーブル駆動ならテーブルの name フィールドを名前にする。例: `t.Run("注文金額3000円で送料を計算すると、送料は無料になる", ...)`)
  - ケースの項目 = ケースの `t.Run` の中で呼ぶ `t.Attr("Given", "...")`。キーは `Given`・`When`・`Then`・`種別`・`正常異常`・`観点`。`観点` は省略可で、観点ごとに `t.Attr("観点", "境界値")` を 1 回ずつ呼ぶ。ステップは、`Given` (省略可)、`When` (手順の数だけ)、`Then` の順に繰り返して呼ぶ。Go 1.25 以降を用いる
    - 項目は `go test -json` の `attr` イベントに、呼んだ順に出る。JUnit 形式には変換されないため、カタログの生成は `go test -json` を読む
  - `go test` は名前の半角空白を `_` に置き換えて出力するため、名前に半角空白を入れない。`[...]` の直後も詰めて書く (例: 「[本体:注文] 送料計算」ではなく「[本体:注文]送料計算」)
  - ケースが 1 つだけのときも、テーブルにはせずその 1 ケースを `t.Run` で書く
    - なぜ: テストケースカタログに全テストがケースの粒度で出力されるようにするため

## [lang/go] コード生成

- 型コードは REST 契約 (OpenAPI 定義) ・Pub/Sub 契約 (AsyncAPI 定義) を SSoT とし、型生成スクリプトで再生成する

## [lang/go] docs コメント

- docs コメントは godoc 形式で書く (識別子名で始める)

## [lang/go] 命名

- ctx / cfg / tx など Go で確立された短縮語は使ってよい
- コンストラクタは New<型> (パッケージの主要型が一つなら New)
  - functional option は With<項目>
- 型変換を関数で表す場合は To<型>
- 型変換をメソッドで表す場合は目的の型名にする
- getter は動詞を付けず対象名そのものにする
- レシーバ名は型を表す 1〜2 文字の短縮にする

## [lang/go] 分岐

- `switch` には必ず `default` 節を書き、想定外の値としてエラーを返す (または panic する)。空の `default` で無言に通過させない
