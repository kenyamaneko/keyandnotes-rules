# テストの書き方

Key and Notes 各プロジェクト共通のテスト規約。`principles.md` から参照される。
言語ごとの書き方 (テーブル駆動・ケースの項目の載せ方等) は `rules/lang/<lang>.md` を見る。

## 基本方針

テストは実装をなぞるのではなく仕様を確かめる。

テストコードが担保する振る舞いをテストファイルを行き来せずに読めるようにするため、テスト名とケースの項目を集めたテストケースカタログを CI で生成する。

## テストの種別

テストは以下の軸で種別に分類する。

- **結合するもの**：実物で動かす部品やサービス
- **モックにするもの**：代用に差し替えるもの
- **実物にするもの**：結合するもの以外で、実物を使うもの。インフラは、コンテナやエミュレータで動かすものも実物として扱う
- **確かめるもの**：テストで確認する振る舞い

外部サービスとは、自分たちが運用しないサービス (例: 決済代行会社・配送業者) を指す。

種別は、ケースごとに決める。

- **単体テスト**：
  - 結合するもの：なし
  - モックにするもの：注入される依存のすべて
  - 実物にするもの：なし
  - 確かめるもの：一つの関数やクラスのロジック (例: 送料計算が注文金額ごとの送料を返す。注文確定の処理が、モックの在庫管理を使って在庫切れを検知する)。
- **部品間結合テスト**：
  - 結合するもの：自アプリの複数の部品
  - モックにするもの：インフラ、自分たちが運用する別のサービス、外部サービス
  - 実物にするもの：なし
  - 確かめるもの：部品どうしの連携 (例: 注文 API を呼び出し、決済代行会社をモックにして、注文が確定する)。
- **インフラ結合テスト**：
  - 結合するもの：インフラにアクセスする部品
  - モックにするもの：自分たちが運用する別のサービス、外部サービス
  - 実物にするもの：インフラ (データベース・ドキュメントストア・キャッシュ・メッセージキューなど)
  - 確かめるもの：インフラに直接アクセスする実装の動作 (例: 注文リポジトリが、データベースのコンテナに注文を保存して読み出せる)。
- **サービス間結合テスト**：
  - 結合するもの：自分たちが運用する別のサービス
  - モックにするもの：外部サービス
  - 実物にするもの：各サービスのインフラ
  - 確かめるもの：その別のサービスとのやり取り (例: 注文サービスが、会員サービスの実物に会員ランクを問い合わせる)。
- **E2Eテスト**：
  - 結合するもの：バックエンドからフロントエンドまでの各モジュール、自分たちが運用する別のサービス
  - モックにするもの：外部サービス
  - 実物にするもの：各サービスのインフラ
  - 確かめるもの：画面から保存先までの経路 (例: 画面の注文ボタンから注文 API とデータベースまでを通し、注文確定の表示が画面に出る)。
- **シナリオテスト**：
  - 結合するもの：自分たちのシステム全体
  - モックにするもの：ローカルでは外部サービス。dev 環境では無し
  - 実物にするもの：各サービスのインフラ。dev 環境では外部サービスも実物
  - 確かめるもの：利用者が目的を達成するまでの一連の操作を最初から最後まで (例: 会員登録からログイン、商品のカート追加、決済まで)。

## テスト生成の手順

実装を読んだのと同じ会話でテストまで書くと、実装の誤りや実装の言葉遣いをそのまま正しい仕様として検証してしまう。仕様を固める工程とテストを書く工程を分けて進める。

1. **仕様抽出**: 対象のコードを読み、その関数が満たすべき仕様を、外部から観測できる言葉の説明文として書き出す。実装の変数名や処理手順など実装側の言葉は使わない。
   - 仕様の各項目はそのままテストのケースになるため、Given・When・Then に分け、「テストの命名」「ケースの書き方」と rules/lang/<lang>.md の命名の割り当てに従った形で書く。
   - 仕様の各項目に、テストの種別を書き添える。シナリオテストの項目には、実行する環境も書き添える。
     - なぜ: テスト生成は実装を読まずに行うため、結合するもの・実物にするもの・モックにするものを仕様から決められる必要があるため。シナリオテストでは、これが環境によって変わる。
   - 仕様の各項目に、付ける観点があれば、「ケースに付ける観点」に従って書き添える。
   - 一つの仕様項目には一つの結論だけを書く。同じ前提から複数の結論を並べるのではなく、結論ごとに項目を分ける (例:「会員ランクが上位のとき、送料が無料になり、ポイント還元率が2倍になる」ではなく、「会員ランクが上位のとき、送料が無料になる」と「会員ランクが上位のとき、ポイント還元率が2倍になる」に分ける)。
   - 一意に定まらない語 (呼び出し先が複数ある場面での「外部サービス」、複数の対象になりうる場面での「状態」のような総称) は避け、その場面で指している具体的な対象を書く (例: 決済代行会社と配送業者の両方に連携するなら、「外部サービスがエラーを返したとき」ではなく「決済代行会社がエラーを返したとき」と書く)。
   - 他の仕様項目を参照するときは、位置関係 (「前の項目の規定に従う」「ここまで通過したとき」など) や、対象が複数いる場面で誰を指すか一意に定まらない代名詞でなく、名指しで参照する。参照先が単独では読めなくなっても意味が通るよう、参照先の結論もその場に書く (例:「送料の計算は上記の規定に従う」ではなく「送料の計算は『送料の基本計算』の規定に従い、合計金額が閾値未満なら固定額を加算する」のように、参照先の結論も併記する)。
     - 仕様抽出ドキュメント自身の章番号も同じ理由で書かない。ドキュメントの構成が変われば意味を失う参照であり、テスト名にそのまま残ると仕様として読めなくなる。
     - 手前の異常系ケースをまとめて「ここまで通過したとき」と指すのも同じ位置関係の参照であり、そのケースが成立する条件を書き出す (例:「会員情報が取得できないとき、送料は 0 円のままになる」「配送先住所が未入力のとき、送料は 0 円のままになる」に続けて「ここまで通過したとき、送料は 500 円になる」と書くのではなく、「会員情報が取得でき、かつ配送先住所が入力されているとき、送料は 500 円になる」のように書く)。
   - 「〜しない」のような否定形は、そこから唯一のアサーション対象が決まるなら問題ない (例:「未登録の要素を削除してもエラーにならない」は、削除後に読み出すと見つからないままになる、という一点しかないので足りる)。決まらないとき (例:「何も更新しない」) は、実際に変化しない状態を名指しする (例:「合計金額はそのままになる」)。テスト生成エージェントは実装を読まないため、文だけでアサート対象が特定できる必要がある。
   - 仕様の記述量を絞るため、書いても新しく確かめられることが無いケースは書かない。
     - 型やその手前のバリデーションによって、その値がそもそも到達しないと言い切れるなら、そのケースは書かない (例: 会員ランクを列挙型で受け取る関数には、列挙型に存在しない値が渡ってきたときのケースを書かない。呼び出し側はその型の値しか渡せないため)。
     - 同じ判断 (例: 受け取ったエラーが一時的なものか恒久的なものかを見分ける基準) が複数の場所で使われているとき (実装で同じ関数を呼んでいるとき) は、その判断の基準を1つの小機能にまとめて書く。他の場所では、その判断の結果どうなるかだけを書けば足りる。
   - 既存のテストがある対象に実装を追加するときは、追加分の仕様項目を、同じ種類の既存の仕様項目 (テスト名) と見比べて粒度をそろえる。既存が確かめていない振る舞い (例: 既存の送料計算のテストが注文金額の境界しか確かめていないのに、追加した割引計算で端数の丸めまで確かめる) や、既存より細かい分割になる項目は、仕様に入れる前にユーザーに確認する。
   - 仕様項目でログの項目名を仕様の言葉に言い換えたときは、言い換えた語がどの項目名を指すかを、Given・When・Then とは別に仕様の補足として書く (例:「エラーの内容」はログの `error` 項目を指す)。テスト生成は実装を読まずに行うため、書かないと、どの項目を確かめればよいか分からない。
   - 同じ形で実装された複数の関数を仕様抽出するときは、一つに書いた振る舞いが他に抜けていないか横断で確認する。加えて、複数の関数が同じ判断基準を共有すると明記した場合は、各関数のセクションの記述がその共有基準と矛盾していないかも確認する (例: 関数Aの説明に「この検証は行わない」と書いてあるのに、関数Bの説明ではその検証を行う前提のままになっていないか)。
2. **仕様レビュー**: 抽出した仕様をユーザーがレビューする。レビューを経てから次の工程に進む。想定と異なる仕様が出てきたら、実装が誤っているのか仕様抽出が誤っているのかを切り分けて修正する。
   - ユーザーに渡す前に、仕様抽出をしたものとは別のサブエージェントか新しい会話に、仕様と、それまでのレビューで出た指摘だけを渡し、本書 (testing.md) の規約に沿っているかを確認させる。指摘は、本書の条文を引用して違反と言い切れるものだけにさせる。
   - 確認は、本書の `##` 見出しの節ごとに1人のレビュアーを立て、同時に走らせる。各レビュアーには、本書の担当する節の見出しと rules/lang/<lang>.md のテスト方針の場所を示し、レビュアー自身に、担当する節とそのテスト方針の原文を、要約や省略をせず全文読ませる。
   - 1回のレビューで見る仕様が多いと確認の深さが落ちる。ファイル単位など扱いきれる単位に区切って回す。
   - 区切ってもなお1ファイルの仕様が過大になるなら、抽出の粒度でなく対象コードの責務分割を疑う。
3. **テスト生成**: レビュー済みの仕様だけを渡してテストコードを書く。実装を読んだ先入観が混ざらないよう、仕様抽出と同じ会話では行わず、サブエージェントか新しい会話で行う。仕様に書かれた種別のとおりに、結合するものと実物にするものは実物のまま、モックにするものはモックにして書く。仕様に書かれた観点は、そのままケースに付ける。既存テストの命名や構造を後から直す場合も同じ分離を適用する。直す理由を仕様の言葉で書き出し、実装を読んでいないサブエージェントか新しい会話に渡して書き直させる。既存テストに観点を後から付ける場合も、実装を読んでいないサブエージェントか新しい会話に、ケースの Given・When・Then の文だけを渡して判断させる。
4. **生成物のレビュー**: テストを書いたエージェントやセッション自身に良否を判定させない。書いたものとは別のサブエージェントか新しい会話に、テストコードと、それまでのレビューで出た指摘だけを渡し、本書 (testing.md) の規約に沿っているかを確認させる。
   - 指摘は、本書の条文を引用して違反と言い切れるものだけにさせる。
   - 確認のしかたは、仕様レビューと同じにする。
   - 観点を後から付けた場合も、付けたエージェントやセッションとは別のサブエージェントか新しい会話が、付けた観点を確認する。

## 種別の選び方

- 関数に固有のロジック (計算式・分類・変換のルールなど) があるなら、期待値を具体値で書く単体テストを作成する。
- ロジックを持たない関数には、単体テストを書かない。固有のロジックを持つ関数まで呼び出し元を遡り、部品間結合テストでカバレッジが通ればよい。
- インフラ (データベース・ドキュメントストア・キャッシュ・メッセージキューなど) に直接アクセスする実装は、ロジックの有無によらず、インフラをモックに差し替えた呼び出し元のテストだけで済ませず、インフラ結合テストを作成する。
- 生成AI (LLM など) を呼び出す実装は、出力が決定的でなく「〜のとき〜が返る」と期待値を断定できないため、dev 環境のシナリオテスト以外のどの種別でもモックに差し替えて確認する。実際のAIへの疎通確認は、dev 環境のシナリオテストとして CI で別に行う。
- 外部サービスなど外へ送る通信を行う実装は、dev 環境のシナリオテストで、そのサービスのサンドボックスなど dev 環境で使える接続先を相手にして確認する。dev 環境で使える接続先が無いときは、テストしない。

## 大原則

- 失敗した時の処理が正しいかを確認するため、正常系だけでなく異常系のケースを作成する。
- リファクタしても壊れないテストにするため、外から観測できる結果だけをアサーションの対象にする。
  - 画面が無い場合は、以下のどちらかでアサーションする。
    - 呼び出し自体が返す結果 (戻り値・例外、応答のステータスや内容など)
    - 呼び出しのあとに別の経路から確認できる変化 (読み直した結果、他の宛先に届いたメッセージやイベントなど)
- 人間がテストの網羅性を確認しやすいように、テスト名と中身を一致させる (仕様の言葉で書く基準は「ケースの書き方」に従う)。
- 既存テストを別の形 (公開経路の検証など) に作り直すときは、置き換え先のテストが通ることを確認してから元のテストを消す。
  - なぜ: 先に消すと、置き換えが完成するまでその仕様が無検証になり、穴が残っても気づけないため。
- 各テストケースは、他のケースの実行順序や結果に影響されず、単独でも成立するようにする。同じ接続・DB・キューなどの状態を複数のケースで使い回すときは、ケースごとに独立した状態から始める。
  - なぜ: 他のケースの影響を受けて失敗しないようにするため。
  - テスト用のデータ作成・削除は、そのテストに関連するものだけを対象にする。
- テストコードに if 文を書かず、条件ごとに独立したテストケースとして並べる。
  - 前提 (Given) にifを使うと、どんなケースが実際に走ったか見えにくく、網羅できているか分かりづらくなる
  - アサーションにifを使うと、条件によって確かめる振る舞いが変わり、別の振る舞いの検証が混ざる。1つのテストは1つの振る舞いを確かめるべきだが、if はこれを壊す。
    ただし単体テスト以外で、後の操作が前の操作の結果に依存する一連の操作 (前の操作をしないと後の操作ができない場合) を、1 つのステップの When に順に並べて1ケースにするのはこの限りではない。
- テストで使う ID と認証情報は、本番の実データのものを使わず、テスト専用のダミー値を用いる。
  - なぜ: 実データの ID は仕様変更でテストが壊れ、本番の認証情報はテストに持ち込むと漏れるため。

## テストの命名

テストケースカタログを生成するため、テスト名だけを読めば仕様がわかるように命名する。

テストの名前は、以下の順で階層化する。

`[区分:大機能(:中機能)]小機能` > ケース

ケースの項目 (ステップの Given・When・Then、種別、正常異常、観点、環境) は、テストの結果に項目として載せる。テスト名は、各ステップの Given・When・Then を読点でつないだ一文にし、ステップが複数のときは「→」でつなぐ。When が複数の操作のときは、操作を読点でつなぎ、最後の操作を「〜すると」の形にする。
  - なぜ: 項目として分けて載せると、Given・When・Then の書き漏らしを機械で止められるため。種別・正常異常・観点は機能の階層を横断する属性であり、階層の段にすると子が 1 つだけの段が連なるため。

例：

- `[本体:注文:業務ルール]送料計算 > 注文金額3000円で送料を計算すると、送料は無料になる` (When「注文金額3000円で送料を計算する」、Then「送料は無料になる」、種別「単体テスト」、正常異常「正常系」)
- `[本体:決済:業務処理]クレジットカードの与信判定 > 利用限度額が5万円のとき、決済 API に注文金額 5万1円を指定して呼び出すと、決済の応答は利用限度額超過を示すエラーになる` (種別「部品間結合テスト」、正常異常「異常系」)

- **区分**：以下から選ぶ。
  - **本体**：利用者や呼び出し元が目的を達成するための業務の振る舞い。
  - **共通**：複数の大機能が使うものと、どのアプリにもある機能。次の大機能を置く。
    - **機能共通**：複数の大機能が使う処理 (例: 日付の書式変換)。どのリポでも同じ名前にする。
    - **画面共通**：複数の大機能が使う画面や画面の部品 (例: ヘッダー・404 画面)。どのリポでも同じ名前にする。
    - **どのアプリにもある機能**：認証・設定など。
  - **運用**：システムを動かし続けるための振る舞い (例: ヘルスチェック・ログ出力・停止処理)。
  - **外部連携**：外部サービスとの入出力 (例: 決済代行会社の応答の変換・配送業者への再送)。
  - **シナリオ**：利用者が目的を達成するまでの一連の操作 (動線)。複数の機能をまたぐ。種別は、シナリオテストにする。
- **大機能**：区分の下の機能。「機能の分類」に従って選ぶ。
- **中機能**：大機能の下の切り口。「機能の分類」に従って選ぶ。
- **小機能**：それ以上分けない機能 (例: 送料計算・会員ランク判定・決済の実行)。利用者から見た機能の単位で決める。関数・モジュール・画面部品の単位では決めない。中機能と小機能を合わせて、何を検証しているかがわかるようにする。
- 小機能の中で、前提の違うケースがばらばらに並ぶときは、前提が同じケースの塊ごとに小機能を分けると、カタログの表が読みやすくなる
  - 例: 小機能「クーポンの利用」で、期限切れの 3 ケースと有効な 1 ケースが混ざるなら、「期限切れクーポンの拒否」と「有効なクーポンの適用」に分ける
- 区分・大機能・中機能は、コードの置き場所 (パッケージ名・ディレクトリ名・レイヤー名) ではなく、検証している機能で決める。
- **ケース**：1 つ以上のステップと、種別・正常異常を持つ。観点を持つこともある。シナリオテストのケースは、環境も持つ (「シナリオテスト」に従う)。
- **ステップ**：Given・When・Then の組。ステップを複数にするのは、シナリオテストと、異常からの回復の確認 (失敗、再試行、成功) だけにする。それ以外のケースは 1 ステップにする
  - なぜ: シナリオテストと異常からの回復の確認は、操作のたびに結果を確かめる必要があるため。それ以外のケースは、結果を確かめるのが最後の操作の後だけでよく、ステップを分ける理由がない
- **Given**：ステップの前提。状態を表す形で書く (「〜しているとき」「〜されているとき」「〜であるとき」「〜のとき」)。テストが確かめる操作は When に書く。それより前に起きた出来事は、起きた後の状態として Given に書いてよい (例: 「注文を確定しているとき」)。任意。前提が無いとき、または直前のステップの結果の状態が前提のときは、省略する
  - 通信の応答の形では書かず、利用者が見る言葉の状態で書く。外部依存が使えないことや、読み込みが終わっていないことも、利用者に見える状態で書く (例: ○「在庫が 0 のとき」「決済代行会社が利用できないとき」「ヒントを読み込み中の表示が出ているとき」、×「在庫 API が在庫 0 を返すとき」「ヒントの要求が完了していないとき」「外部サービスをモックにした環境で」)
- **When**：ステップの操作。実行する順に並べた手順で書く。1 つの操作を「〜する」の形で書く。必須。操作が階層から自明でも書く。
  - 各操作は、テストが入る入口に合わせて書く
    - 画面から入るとき：どの画面の、どの機能で、画面に見えるボタンや入力欄をどう操作するか。画面名と機能名 (小機能の名前に使う語) を含める (例: ○「カート画面の送料の表示で、配送先に『北海道』を選ぶ」、×「配送先を選ぶ」)
    - API から入るとき：どの API を、どの入力で呼ぶか (例: 「送料計算 API に、配送先『北海道』を指定して呼び出す」)
    - 画面でも API でもない入口から入るとき：小機能の業務操作の名前に、対象と入力を添える (例: ○「注文金額3000円で送料を計算する」、×「送料を計算する」)
  - When には、結果を含まない操作だけを書く。結果や判定は Then に書く (例: ○「カート画面を開く」、×「カート画面で、送料無料の表示を出す」)
  - 入力値が結果を左右する理由が状態 (データ・設定・外部の状況) のときは、理由を Given に書き、When には操作と入力値だけを書く (例: ○ Given「クーポン『SPRING』の有効期限が過ぎているとき」と When「クーポンコード『SPRING』を入力する」、×「有効期限を過ぎたクーポンコード『SPRING』を入力する」)
  - 入力値が結果を左右する理由が製品の仕様 (判定基準・計算規則・業務ルール) のときは、理由を Given に書かず、When の入力と Then の結果の組で仕様を表す (例: ○ When「送料計算 API に、注文金額3000円を指定して呼び出す」と Then「送料は無料になる」、×「注文金額が3000円以上なら送料が無料になるとき」を Given に書く)
  - 時間の経過は、利用者が見る状態の変化が終わるまで待つと書く (例: ○「バナーの表示が終わるまで待つ」、×「バナーの表示開始から 600 ミリ秒待つ」)
  - 同じ操作を繰り返すときは、操作をそのまま繰り返して書く (例: ○「注文確定ボタンを押す」を 2 回並べる、×「直前と同じ操作を行う」)
- **Then**：ステップの結果。観測点まで書く。必須。環境によって結果が違うシナリオテストのステップは、環境ごとに書く (「シナリオテスト」に従う)。
- **種別**：「テストの種別」から選ぶ。単体テストにも種別を書く。
- **正常異常**：以下から選ぶ。必須。カタログだけで正常系・異常系を見分けられるようにするため。
  - **異常系**：Given か When に、意図した使われ方から外れた入力・状態 (呼び出し側の誤り、外部依存の失敗、ユーザーの異常操作など) が含まれるケース。結果 (Then) が呼び出し元にエラーとして返るか、正常応答として返るかは問わない。
  - **正常系**：異常系に当たらないケース。警告が表示されるだけで操作を続行できるケースは、正常系に含む。
- **観点**：任意。「ケースに付ける観点」から選ぶ。

- どの構文が「`[区分:大機能(:中機能)]小機能`」「ケース」と、ケースの項目 (ステップの Given・When・Then、種別、正常異常、観点、環境) に当たるかは言語で異なる。rules/lang/<lang>.md に従う。

## ケースの書き方

- テスト関数・テストクラスには docs コメントを付与しない。テストケースの意図やシナリオも、コメント (docs コメントを含む) で説明してはいけない。コメントを書くと、仕様の記述がテスト名とコメントに分散し、テスト名だけで仕様がわかる状態が崩れる。
- 前提 (Given) には、値を変えると結果 (Then) が変わる前提だけを書く。省略すると結果の条件が読み取れなくなる前提は、省略しない。
  - 例:「会員ランクが上位で、配送希望時間帯が午前のとき、注文確認画面を開くと、送料の表示は無料になる」のように、送料の判定に関係のない配送希望時間帯まで書かない。会員ランクが上位であることだけを示せば足りる。
  - 例:「上位ランクになる」のように、どの累計ポイントのときの話か読めないケースにしない。「累計ポイントが 10000 pt 以上のとき、上位ランクになる」のように前提から書く。定数や不変条件を確かめるテストのように、前提が対象そのものに含まれる場合はこの限りではない。
- 複数のケースが同じ前提・同じ操作・同じ結果を持つときも、ケースごとに、同じ Given・When・Then を同じ文で書く。書き手が重複を避けて言い換えたり、共通の見出しをテストに作ったりしない
  - なぜ: 同じ文で並べると、カタログが同じ Given・When を表のセルにまとめられる。Given・When・Then の書き漏らしも、機械で止められる。Then は、同じ結果を別の文で書くと、同じ結果を確かめているケースかどうかが読み取れなくなる
- Given だけが異なり Then が完全に同一な複数ケースは、テーブル駆動に統合する。
- テーブル駆動 (データ駆動) では、行ごとにケースを定義し、各行が Given・When・Then を持つ。
  - 行のパラメータを Given・When・Then の文に埋め込むときは、文が日本語として読めるように書く。空文字のように見えない値は「空文字」のような言葉のラベルに置き換える。
- 前提 (Given) と結果 (Then) の値は具体値で書く。テストを実装の書き写しにしないためである。「保存した値で返る」のような抽象的な表現ではなく、「注文の配送先の郵便番号が『150-0001』で保存されているとき、取得した注文の配送先の郵便番号は『150-0001』になる」のように書く。
  - ただし、具体値がテスト専用のダミーで、検証対象が値そのものでなく境界の関係なら、「下限のとき」「上限のとき」のような相対表現でよい。
  - 実行タイミングや環境に依存して具体値が書けないもの (日時・パスなど) は、具体値の代わりにその値が何であるかを書く (例:「注文日時が 2026-09-26 03:15 になる」ではなく「注文日時が注文を確定した日時になる」)。
- Given・When・Then に書く値は、その項目に実際に入る種類の値で書く (例: ○商品のレビュー文『とても丈夫で長持ちします』、×『review』『x』)。
- リストの全要素が値の範囲内にあることを条件とするときは、範囲ではなく、下限の値の要素と上限の値の要素を両方含むリストで書く。
  - 例: カート内のすべての商品の価格が 3000 円以上 5000 円以下のとき、まとめ買いクーポンを使えるなら、「カート内の商品の価格が 3000 円から 5000 円の範囲のとき、まとめ買いクーポンを使える」ではなく、「カートに価格 3000 円の商品と価格 5000 円の商品があるとき、まとめ買いクーポンを使える」と書く。
- Given・When・Then など自由文で書ける箇所は日本語の仕様の言葉で書く。語の選び方 (英語の一般語を地の文に混ぜない等) は documentation.md に従う。
  - ただし、利用者が画面・API・保存形式・設定でそのまま見る/触る名前・値は、日本語に言い換えずそのまま使う (例: キー名、列挙値、NaN のような特殊値、HTTP ステータスコード、環境変数名、画面の実文言、JSON・UTC のような定着した略語)。
- 外部を読み書きするコード (リポジトリ・アダプタなど) のテストは、そのコードの操作の言葉 (保存する・取得する・変換するなど) で書いてよい。ただし、確かめている性質が利用者にも見えるもの (表示のされ方・許可されるかどうかなど) なら、利用者の言葉で書く。
- 仕様の言葉で名付けられないときは、名前の付け方ではなく設計を疑う。実在しない言葉を発明して取り繕わず、公開された入口を通さず内部の変換や伝搬だけを検証していないか (「アンチパターン」の変換関数直接テストなど) を確認する。
- テスト名に実装の言葉を含めてはいけない。実装の言葉とは、仕様の利用者が使わず、実装を読んで初めて出てくる語であり、変数名・関数名のような識別子に限らず、引数・戻り値のようにプログラムの構造を指す語も含む (例: ×「呼び出し元に返る送料は 500 円になる」「送料計算結果の送料は 500 円になる」「乱数が 0.9999 のとき」、○「送料は 500 円になる」「ポイント還元の抽選に外れたとき」)。
  - 小機能も同様で、テストする関数の名前をそのまま使ったり、括弧で添えたりしない。テストする関数はファイルの場所から特定できる。
- 結果 (Then) に観測点の無い動詞を使ってはいけない。
  - 例:「上位ランクの特典が反映される」だけでは、どこで確認できるかが分からない。「会員ランクを上位にすると、注文確認画面に送料無料の表示が出る」のように、結果をどこで観測できるか (どの画面・応答・取得結果) まで書く。
- エラーを返すケースの結果 (Then) は、エラーの原因を利用者の言葉で書く。
  - 例: 「在庫が無い商品を注文したとき、注文の応答は在庫切れを示すエラーになる」。
- テストが注入したダミー値を、本番の仕様値であるかのように名前へ書いてはいけない。
  - 例: テストでは閾値を 1000 pt に差し替えているのに、「累計ポイントが 1000 pt 以上のとき、上位ランクになる」と書くと、読者は 1000 pt を仕様の閾値 (実際は 10000 pt) だと誤認する。仕様値でないなら「設定した閾値以上のとき、上位ランクになる」のように相対表現で書く。
- テスト名や括弧の注記に実現方法 (How) を書いてはいけない。
  - 例: 「送料計算 (合計金額 × 0.1 で算出)」のように計算式を注記しない。前提 (Given)・操作 (When)・結果 (Then) だけを書けば十分で、実現方法は実装を読めば分かる。
- Given・When・Then に、本文と同じ対象を指す別の語を括弧で添えない。名前に番号や識別子を添える場合も同じ (例: ×「在庫が 0 (売り切れ)」「会員ランク『ゴールド』(rank-3)」、○「会員ランク『ゴールド』」)。どちらかの語に統一する

## 機能の分類

- **大機能**：本体と共通では、利用者から見たアプリの機能のうち、アプリの機能を説明するための一番大きい単位にする。画面・API・内部の部品の違いで分けない (例: 送料の計算規則と送料の画面表示は、どちらも大機能「注文」に入れる)。画面のメニュー名や仕様書の機能名と同じ名前にする。運用では運用する対象の名前にする
  - 複数の大機能が使うものは、区分「共通」の大機能「機能共通」か「画面共通」に入れる。使う大機能が一つに収まるものは、その大機能に入れる
- **中機能**：大機能の下で、同じ切り口の小機能を束ねる名前にする (例: 大機能「注文」の中機能「画面表示」「業務ルール」「保存と取得」)。ケースの Given・When・Then から判断できないときは、付けない
  - 中機能は、運用では置かない。本体・共通・外部連携では任意。シナリオでは動線の種類にする。
  - 中機能の語彙の出発点として、画面表示・画面遷移・入力・操作・業務ルール・業務処理・保存と取得のような切り口を使ってよい。出発点であり、この語に縛られない
  - 画面遷移のように、種別をまたいで現れる切り口も中機能にする。種別は、どこまで実物で動かすかを表し、機能の分類とは別の軸のため

## ケースに付ける観点

テストの質を人間が見やすくするため、ケースに観点を付けられる。観点は次の 6 個だけで、他の値は使わない。

- 観点を付けるかどうかは任意で、1 つも付かないケースがあってよい。迷ったら付けない
- 1 つのケースに複数の観点を付けてよい。同じ観点を重ねて付けない。境界値と同値分割は同時に付けない

観点の値と、付ける条件は次のとおり。

- **境界値**：結果が切り替わる閾値の隣り合う値 (ちょうど・直前・直後)、または値域の最小・最大を前提にしたケース。回数や件数が上限・下限に達する瞬間も含む。境界値のケースにする値は、「ロジックのテスト」に従う
  - 例: 注文金額が 3000 円以上で送料が無料になるとき、注文金額が 2999 円のケースと 3000 円のケース。クーポンの利用回数の上限が 3 回のとき、3 回目の利用のケース
- **同値分割**：同じ結果になる値のグループから代表を 1 つ選んだケース。同じ小機能に、別のグループを代表する兄弟ケースがあるときに付ける
  - 例: 配送先の地域区分ごとに送料が決まる小機能で、関東の代表として配送先が「東京都」のケース
- **エッジケース**：通常の操作では起こらない状況、画面から入力できない値、仕様上ほぼ到達しない値を前提にしたケース。他の観点と同時に付けてよい
  - 例: 福引きの抽選で、乱数が最大値に近い 0.9999 のとき。値域の端でもあるので、境界値とエッジケースの両方を付ける
- **件数・有無**：0 件・1 件・複数件、または「無い」と「空」の違いが入力の軸になっているケース。件数や有無で書き分けるケースは、「ロジックのテスト」に従う
  - 例: カートの商品が 0 件・1 件・複数件のとき。注文のメモが無いときと、注文のメモが空文字のとき
- **外部依存の失敗**：データベース・AI・外部 API・ネットワークなど、自分のコードの外が失敗・タイムアウト・不正な応答を返すことを前提にしたケース
- **回復確認**：失敗の後に再試行や次の正常な操作をして、成功すること (失敗時の表示や状態が残らないこと) を確かめるケース。回復の確認の書き方は、「異常系からの回復」に従う

## テストケースカタログの生成

- テストケースカタログは、区分・大機能・小機能の順に見出しの入れ子を作り、小機能の下に、ケースの表 (Given・When・Then・タグ) を置く。中機能は見出しにせず、大機能の中で小機能を中機能ごとにまとめて並べる。区分がシナリオのときだけ、小機能の名前の横に中機能 (動線の種類) を表示する。
- 表は、小機能の中のケースを Given、When の順に並べ替える。Given が同じ行は Given のセルを、Given と When が同じ行は When のセルを、1 つにまとめる。ケースの数や Given・When の共有の仕方によらず、全ケースが同じ形の行になる。When は、番号つきの手順で表示する。ステップが複数のケースは、ステップごとに Given・When・Then の行を並べ、タグは 1 回だけ表示する。正常異常、種別、観点は、ケースのタグとして表示する。タグの並びも、正常異常、種別、観点の順にする。
- 環境ごとの Then を持つステップは、Given・When のセルを結合し、Then を環境ごとのセルに分ける。
- 大機能ごとに仕様を追えるようにするため、カタログは正常異常と種別で絞り込めるようにする。テストの質を人間が見やすくするため、観点でも絞り込めるようにする。絞り込みの並びは、正常異常、種別、観点の順にする。観点が無いケースを絞り込む選択肢「タグなし」を置く。
- カタログの見た目は次のとおりにする。
  - 種別と観点は、値ごとに色を分け、枠と文字を同じ色にする
  - 正常系は緑、異常系は桃で塗りつぶし、文字は画面の背景色にする
  - 表の行の背景は、全行同じ色にする
  - タグは、各ケースの行にだけ表示する
  - 表のヘッダーの文字は 12px にする
- テストケースカタログの生成は、スキップしていないケースに、種別・正常異常が無いとき、ステップが無いとき、いずれかのステップに When か Then が無いとき、観点が「ケースに付ける観点」で定めた値以外のとき、同じ観点が重ねて付いているとき、境界値と同値分割が同時に付いているとき、エラーにする。Given が無いことと、観点が無いことは、エラーにしない。
- テストケースカタログの生成は、スキップしていないケースの環境と環境ごとの Then について、次の場合にエラーにする。
  - シナリオテストのケースに環境が無いとき、環境が ローカル・dev環境 以外のとき、同じ環境が重ねて付いているとき
  - シナリオテスト以外のケースに、環境か環境ごとの Then があるとき
  - 環境ごとの Then が、ケースの環境と一致しないとき、2 つ未満のとき、全て同じ内容のとき、同じ環境で 2 つあるとき、同じステップの Then と混ざっているとき

## ロジックのテスト

ロジックを確かめるテストに適用する。

- 条件によって扱いが変わる境界ごとに、その境界で隣り合う二つの値だけを、境界値のケースにする (例: 整数で、注文金額が3000円以上なら2999円と3000円、3000円以上5000円以下なら2999円と3000円、5000円と5001円)。
- 件数や有無で扱いが変わるなら、0 件・1 件・複数件、「無い」と「空」をケースに分ける。

## 乱数の扱い

乱数を使う機能のテストに適用する。

- 単体テストから、ローカルで動かす E2E テストとシナリオテストまでは、乱数を `port` 越しに固定値の実装へ差し替え、期待値を具体値で書く。
  - なぜ: 乱数に依存する期待値は実行のたびに結果が変わり、失敗を再現できないため。
  - 例: クーポンの当せん抽選を、必ず当せんする乱数に固定し、クーポンを使うと、割引が適用される。
- 本物の乱数を使うのは、実環境を相手にするテスト (例: dev 環境のシナリオテスト) に限る。このとき、結果の具体値は断定せず、性質で確かめる。
  - 例: 当せん抽選の結果が、当せんか落選のどちらかになる。
- 乱数を使う処理の偏りや境界は、乱数の値を指定する単体テストで確かめる。E2E テストとシナリオテストでは確かめない。
- 固定値の乱数の実装には、どの値に固定したかと、その値がどの結果を選ぶかを Why コメントとして書く。

## 入口と結果の確認

単体テスト以外のテストに適用する。

- 途中の状態を手で用意して割り込ませず、公開された入口 (API・画面操作など)から実行する。
  - なぜ: 途中から始めると、入口から結果までの経路が壊れていても気づけないため。
- 操作した結果まで確かめる。「例外が出ない」「エラーが無い」「件数が合う」だけで終えず、操作の後に実際にどうなったか (保存された内容・返ってきた値・変化した状態) まで踏み込む。
- 二重送信の防止は、同じ操作を 2 回続けて行い、保存された内容が 1 件だけであることを確かめる。

## 異常系からの回復

単体テスト以外のテストに適用する。

- 異常系の確認は失敗した状態を見るだけで終えず、そこからの回復まで確認する。再試行 (または次の正常な操作) をすると成功すること、失敗時に出た状態 (エラー表示など) がその後の操作まで残り続けないことを確かめる。
  - なぜ: 失敗時の表示や状態を出しっぱなしにする不具合は、失敗した瞬間だけを確認するテストでは検知できないため。
  - 回復の確認は、失敗後の状態が同じ異常系の間では繰り返さず、その状態ごとに一つ確かめる。失敗後の状態とは、失敗の直後に利用者や呼び出し元から観測できる表示・保存内容・次に取れる操作を指す。
    - なぜ: 経路が異なる異常系でも、失敗後の状態が同じなら回復の振る舞いは変わらないため。

## 接続先が使えない環境での失敗

単体テスト以外のテストに適用する。

- 接続先 (エミュレータ・DB コンテナ・別のサービスなど) が使えない環境では、テストを沈黙スキップせず失敗させる。
  - なぜ: スキップが常態化すると、検証されていないのに全体が通ったように見えるため。

## E2Eテストとシナリオテストの実行環境

- E2Eテストとシナリオテストは、テスト専用の環境で実行する。dev 環境は、テスト専用の環境として扱う。

## シナリオテスト

- シナリオテストは、利用者が目的を達成するまでの一連の操作 (動線) を最初から最後まで確かめる。
  - なぜ: 部品間結合テストやサービス間結合テストが通っていても、全体を動かしたときに利用者が目的を達成できるかは確かめられないため。
- 動線の種類は次のとおり。
  - **通常の動線**：会員登録・ログイン・商品の閲覧・カートへの追加・決済を最後まで通す。
  - **異常から回復して目的を達成する動線**：決済に失敗したあと、再試行して注文を確定する。
  - **最終的にエラーになる動線**：在庫が無い商品を注文し、注文できないエラーが表示される。
  - **利用者設定を挟む動線**：配送先を変更してから注文を確定する。
- シナリオテストの名前は、「テストの命名」と「機能の分類」の区分・大機能・中機能・小機能の規定の例外とする。区分は「シナリオ」、大機能は利用者の目的 (例: 「商品を購入する」)、中機能は動線の種類 (上の4つから選ぶ)、小機能は動線の始点と終点 (例: 「会員登録画面から注文完了画面」) にする。
  - なぜ: 動線は複数の機能をまたぐため、機能の階層に入れると、どの機能に属するかを決める根拠がなくなるため
- シナリオテストのケースは、複数のステップで書く。操作のまとまりごとにステップを分け、ステップごとに結果を確かめる
- シナリオテストのケースは、実行する環境を「環境」の項目で持つ。値は ローカル・dev環境 から 1 つ以上選ぶ。シナリオテスト以外のケースは「環境」を持たない
  - 同じ動線を 2 つの環境で確かめるときは、ケースを 1 つ書き、環境に両方を付ける。Given・When は環境によらない文で書く
  - ケースの環境に含まれない環境では、そのケースはないものとして扱い、スキップにしない
    - なぜ: スキップは、実行すべきケースを実行しなかったことを表す。環境が違って対象外なことと、意味を分けるため
- 環境によって結果が違うステップだけ、Then を環境ごとに書く。結果が同じステップは、Then を 1 つにする
  - 例: 配送料を、ローカルでは固定の金額、dev 環境では配送業者の見積もりが返す金額の範囲として確かめる
  - 環境ごとの Then は、ケースの環境すべてについて書く。環境ごとの Then を書いたときは、どれか 2 つが互いに違う内容になる
  - 環境ごとの結果は、テストの本体の分岐でなく、環境ごとの期待値の表から値を引いて確かめる
- dev 環境を持つシナリオテストは、dev へのデプロイ後に CI で実行する


## GUI (画面) のテスト

画面を持つアプリのテストに適用する。

- 画面に見える結果で判断する。画面の切り替わり・表示内容・エラー表示を確かめる。画面を組み立てる内部の部品への呼び出しや内部の値は検証しない。
- 部品間結合テストでモックにするのは外部との境界だけ。通信・WebSocket・ログインなどを代用に差し替え、画面を組み立てる内部の部品は実物を使う。
  - なぜ: 部品どうしの連携が壊れていても気づけるようにするため。
- API 通信のモックは HTTP 境界 (ネットワーク層) で行う。api クライアント / モジュールを直接差し替えない。
  - なぜ: api モジュールを差し替えるとリクエスト組み立て〜レスポンス処理の経路が飛ばされる。ネットワーク層でモックすれば実際の通信経路を通して検証できるため。
- 見た目や実装の詳細に依存させない。CSS クラス名・アニメーションの文字列・配置の係数・固定の待ち時間などを確かめの対象にしない。
  - なぜ: 見た目を変えただけで壊れ、ユーザーに見える動きを確かめていないため。
- 要素を探す・確かめるときは、画面に見えるテキストや role を優先する。テキストや role が同じまま裏側の状態だけ変わる場合など、見た目だけでは区別できないときに限り、role / aria-* / data-state のような意味を持つ属性で確かめる。data-testid のような実装専用の識別子は、それでも区別できないときの最終手段とする。
  - なぜ: テキストや role は画面に見える情報でユーザー体験と直結するが、data-testid は画面に現れず、コンポーネントの実装が変わっただけでテストが壊れる。
- 操作は実際のユーザー操作として発火させる。内部のイベントハンドラを直接呼ばない。
- 二重送信の防止は、同じ操作を 2 回続けて行い、1 回目の後に再度の操作ができない状態 (例: ボタンが無効になる・処理中の表示が出る) になること、または 2 回の操作の後に画面へ表示される結果が 1 つだけであること (例: 注文一覧に 1 件だけ表示される) を確かめる。
- 応答が届く順序で結果が変わる振る舞い (例: 商品一覧の絞り込みを切り替えたとき、遅れて届いた前の絞り込みの応答で一覧が上書きされない) は、境界のモックの応答を返すタイミングをテストが制御し、先に送った要求への応答を後から返して確かめる。
  - なぜ: 固定時間の遅延で応答を遅らせると、待ち時間より先にアサーションが終わった場合に、遅れた応答が届く前に判定してしまい、上書きの不具合を検知できないため。

## アンチパターン

- テストは、ビルドが通ることだけで完了としてはいけない。
  - 例: ビルドが通ることを確認しただけで、テストを実行して確かめたことにする。ビルドが通ることは構文や型が合っていることを示すだけで、クエリや外部呼び出しが正しく動くかどうかは確認できていない。
- 入力と出力の対応を、変換関数を直接呼んで突き合わせてはいけない。
  - 例: エラー→HTTP ステータスの変換関数を単体で呼び、対応を 1 件ずつ確かめる。コードの分岐を書き写しただけで、その状況で本当にその出力が返るかは確かめていない。
  - 除外: 契約の SSoT が、実際の通信を介してこの変換を確かめている場合。
- 生成物の文字列を期待文字列とそのまま突き合わせてはいけない。
  - 例: 生成した SQL やコードを文字列比較で確かめる。書式を変えただけで壊れやすく、実行した結果が正しいかは確かめていない。
  - 完全一致を部分一致に緩めても、実行した結果を確かめていない点は変わらない。生成物を実行し、その結果 (更新された行・出力された内容) を確かめる。
- 依存を欠けた状態で渡し、早期エラーだけを確かめてはいけない。
  - 例: ハンドラに依存を欠けた状態(nil/null/未設定など) で渡し、入力エラーの 400 や「落ちない」ことだけを確かめる。本来の処理(依存を呼んで結果を返す) に届かず、配線の欠落を見逃す。
- モックが「呼ばれたこと」「呼ばれた回数」だけを確かめて終えてはいけない。
  - 例: 配信関数が 1 回呼ばれたことだけを確かめる。誤った内容が渡っていても緑のままになる。操作の後に実際に起きた結果 (保存・配信された内容) まで確かめる。
- 異常系で、失敗した (エラーになった・例外が飛んだ) ことだけを確かめて終えてはいけない。
  - 例: 認証ヘッダが無い場合とトークンが無効な場合のように、原因が異なるのに同じステータスコードや同じ例外型になる分岐がある。両方のテストがステータスコード・例外の型だけを確かめていると、片方の分岐が誤ってもう片方の理由を返しても検知できない。返ってきたエラーメッセージや種類など、原因を区別できる内容まで確かめる。
  - メッセージを指定しない `toThrow()` も同様の弱さを持つ。別の原因のエラーが飛んでも通ってしまうため、想定した原因のエラーであることまで確かめる。
- 結果が存在することだけを確かめて終えてはいけない。
  - 例: 注文確認メールの本文が空でないことだけを確かめる。本文が別の注文のものでも緑のままになる。本文に含まれる注文番号など、期待する内容まで確かめる。
- 同じプロセス内の部品に渡された引数を確かめてはいけない。
  - 例: 送料計算が会員ランク判定に会員 ID をそのまま渡したことを、差し替えた判定が受け取った引数から確かめる。引数は外から観測できず、リファクタで壊れる。送料など外から観測できる結果で確かめる。
- 不具合修正のあとに追加するテストは、直した不具合の再発だけをピンポイントで確かめてはいけない。
  - 例: 「送料が負の値にならない」のように、修正前に起きていた症状が出ないことだけを確かめる。同じ処理に潜む別の不具合には反応せず、本来の仕様に沿った期待値 (例: 「送料は 500 円になる」) を確かめれば、直したバグも含めて仕様から外れる結果を検出できる。
- 期待値をアサートした上に、その裏返しの「起こらないこと」を重ねて確かめてはいけない。
  - 例: 送料が 500 円であることを確かめた上で、さらに送料が -1 円でないことも確かめる。期待値のアサーションが通れば否定は自動的に成り立ち、何も確かめを足していない。
- 実装をテストに書き写してはいけない。
  - 例: フィールドのコピーや定数をそのまま写す、期待値をテストするコードと同じ計算で作る。実装とテストが二重管理になり、両方に同じバグが入れば気づけない。
  - 本番コードの定数や関数を取り込んで期待値を組み立てるのも同じ書き写しであり、定義が誤っていても両側が同時に変わり検出できない。期待値はテスト側のリテラルで書く。
  - 除外: 純粋な関数 (計算式・分類・命名規則) を具体値で直接確かめる場合。
- 環境に dev環境 を持つシナリオテストを、モックの外部サービスに向けて実行してはいけない。
  - 例: 決済代行会社の API に本当に接続できるかを確かめる dev 環境のシナリオテストを、モックサーバーに向けて実行する。実物に接続できるかは何も確かめていない。
- 本番に無い検証ロジックをテスト内で作って確かめてはいけない。
  - 例: 本番に存在しないロジックや変換をテスト内に書き、自前の入力に当てる。テスト内で完結し、本番コードを何も通っていない。
- モック自体の動作を確かめてはいけない。
  - 例: 決済代行会社のモックサーバーが、受け取った金額をそのまま返すことを確かめる。本番のコードを何も通っておらず、モックが実物とずれても検知できない。
- テストするコードでないライブラリそのものの挙動を確かめてはいけない。ライブラリの品質はライブラリ開発者の責任であり、このプロジェクトで検証しても仕方がない。
