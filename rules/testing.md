# テストの書き方

Key and Notes 各プロジェクト共通のテスト規約。`principles.md` から参照される。
言語ごとの書き方 (テーブル駆動・入れ子等) は `rules/lang/<lang>.md` を見る。

## 基本方針

テストは実装をなぞるのではなく仕様を確かめる。

仕様の全体像をテストファイルを行き来せずに読めるようにするため、テスト名を集めたテスト観点カタログを CI で生成する。

## テストの種別

テストは以下の観点で種別に分類する。

- **結合するもの**：実物で動かす部品やサービス
- **モックにするもの**：代用に差し替えるもの
- **実物にするもの**：結合するもの以外で、実物を使うもの。インフラは、コンテナやエミュレータで動かすものも実物として扱う
- **確かめるもの**：テストで確認する振る舞い

外部サービスとは、自分たちが運用しないサービス (例: 決済代行会社・配送業者) を指す。

種別は、ケースごとに決める。

- **単体テスト**：
  - 結合するもの：なし
  - モックにするもの：注入される依存のすべて
  - 実物にするもの：なし
  - 確かめるもの：一つの関数やクラスのロジック (例: 送料計算が注文金額ごとの送料を返す。注文確定の処理が、モックの在庫管理を使って在庫切れを検知する)。
- **部品間結合テスト**：
  - 結合するもの：自アプリの複数の部品
  - モックにするもの：インフラ、自分たちが運用する別のサービス、外部サービス
  - 実物にするもの：なし
  - 確かめるもの：部品どうしの連携 (例: 注文 API を呼び出し、決済代行会社をモックにして、注文が確定する)。
- **インフラ結合テスト**：
  - 結合するもの：インフラにアクセスする部品
  - モックにするもの：自分たちが運用する別のサービス、外部サービス
  - 実物にするもの：インフラ (データベース・ドキュメントストア・キャッシュ・メッセージキューなど)
  - 確かめるもの：インフラに直接アクセスする実装の動作 (例: 注文リポジトリが、データベースのコンテナに注文を保存して読み出せる)。
- **サービス間結合テスト**：
  - 結合するもの：自分たちが運用する別のサービス
  - モックにするもの：外部サービス
  - 実物にするもの：各サービスのインフラ
  - 確かめるもの：その別のサービスとのやり取り (例: 注文サービスが、会員サービスの実物に会員ランクを問い合わせる)。
- **E2Eテスト**：
  - 結合するもの：バックエンドからフロントエンドまでの各モジュール、自分たちが運用する別のサービス
  - モックにするもの：外部サービス
  - 実物にするもの：各サービスのインフラ
  - 確かめるもの：画面から保存先までの経路 (例: 画面の注文ボタンから注文 API とデータベースまでを通し、注文確定の表示が画面に出る)。
- **シナリオテスト**：
  - 結合するもの：自分たちのシステム全体
  - モックにするもの：外部サービス
  - 実物にするもの：各サービスのインフラ
  - 確かめるもの：利用者が目的を達成するまでの一連の操作を最初から最後まで (例: 会員登録からログイン、商品のカート追加、決済まで)。
- **スモークテスト**：
  - 結合するもの：外部サービス (サンドボックスを含む)
  - モックにするもの：なし
  - 実物にするもの：なし
  - 確かめるもの：最低限の呼び出しが成功すること (例: 決済代行会社のサンドボックスに接続し、与信の呼び出しが成功する)。

## テスト生成の手順

実装を読んだのと同じ会話でテストまで書くと、実装の誤りや実装の言葉遣いをそのまま正しい仕様として検証してしまう。仕様を固める工程とテストを書く工程を分けて進める。

1. **仕様抽出**: 対象のコードを読み、その関数が満たすべき仕様を、外部から観測できる言葉の説明文として書き出す。実装の変数名や処理手順など実装側の言葉は使わない。
   - 仕様の各項目はそのままテストのケースの名前になるため、「テストの命名」と rules/lang/<lang>.md の命名の割り当てに従った形で書く。
   - 仕様の各項目に、テストの種別を書き添える。
     - なぜ: テスト生成は実装を読まずに行うため、結合するもの・実物にするもの・モックにするものを仕様から決められる必要があるため。
   - 一つの仕様項目には一つの観点だけを書く。同じ前提から複数の結論を並べるのではなく、結論ごとに項目を分ける (例:「会員ランクが上位のとき、送料が無料になり、ポイント還元率が2倍になる」ではなく、「会員ランクが上位のとき、送料が無料になる」と「会員ランクが上位のとき、ポイント還元率が2倍になる」に分ける)。
   - 一意に定まらない語 (呼び出し先が複数ある場面での「外部サービス」、複数の対象になりうる場面での「状態」のような総称) は避け、その場面で指している具体的な対象を書く (例: 決済代行会社と配送業者の両方に連携するなら、「外部サービスがエラーを返したとき」ではなく「決済代行会社がエラーを返したとき」と書く)。
   - 他の仕様項目を参照するときは、位置関係 (「前の項目の規定に従う」「ここまで通過したとき」など) や、対象が複数いる場面で誰を指すか一意に定まらない代名詞でなく、名指しで参照する。参照先が単独では読めなくなっても意味が通るよう、参照先の結論もその場に書く (例:「送料の計算は上記の規定に従う」ではなく「送料の計算は『送料の基本計算』の規定に従い、合計金額が閾値未満なら固定額を加算する」のように、参照先の結論も併記する)。
     - 仕様抽出ドキュメント自身の章番号も同じ理由で書かない。ドキュメントの構成が変われば意味を失う参照であり、テスト名にそのまま残ると仕様として読めなくなる。
     - 手前の異常系ケースをまとめて「ここまで通過したとき」と指すのも同じ位置関係の参照であり、そのケースが成立する条件を書き出す (例:「会員情報が取得できないとき、送料は 0 円のままになる」「配送先住所が未入力のとき、送料は 0 円のままになる」に続けて「ここまで通過したとき、送料は 500 円になる」と書くのではなく、「会員情報が取得でき、かつ配送先住所が入力されているとき、送料は 500 円になる」のように書く)。
   - 「〜しない」のような否定形は、そこから唯一のアサーション対象が決まるなら問題ない (例:「未登録の要素を削除してもエラーにならない」は、削除後に読み出すと見つからないままになる、という一点しかないので足りる)。決まらないとき (例:「何も更新しない」) は、実際に変化しない状態を名指しする (例:「合計金額はそのままになる」)。テスト生成エージェントは実装を読まないため、文だけでアサート対象が特定できる必要がある。
   - 仕様の記述量を絞るため、書いても新しく確かめられることが無いケースは書かない。
     - 型やその手前のバリデーションによって、その値がそもそも到達しないと言い切れるなら、そのケースは書かない (例: 会員ランクを列挙型で受け取る関数には、列挙型に存在しない値が渡ってきたときのケースを書かない。呼び出し側はその型の値しか渡せないため)。
     - 同じ判断 (例: 受け取ったエラーが一時的なものか恒久的なものかを見分ける基準) が複数の場所で使われているとき (実装で同じ関数を呼んでいるとき) は、その判断の基準を1つの小機能にまとめて書く。他の場所では、その判断の結果どうなるかだけを書けば足りる。
   - 既存のテストがある対象に実装を追加するときは、追加分の仕様項目を、同じ種類の既存の仕様項目 (テスト名) と見比べて粒度をそろえる。既存が確かめていない観点 (例: 既存の送料計算のテストが注文金額の境界しか確かめていないのに、追加した割引計算で端数の丸めまで確かめる) や、既存より細かい分割になる項目は、仕様に入れる前にユーザーに確認する。
   - 仕様項目でログの項目名を仕様の言葉に言い換えたときは、言い換えた語がどの項目名を指すかを、ケースの名前とは別に仕様の補足として書く (例:「エラーの内容」はログの `error` 項目を指す)。テスト生成は実装を読まずに行うため、書かないと、どの項目を確かめればよいか分からない。
   - 同じ形で実装された複数の関数を仕様抽出するときは、一つに書いた観点が他に抜けていないか横断で確認する。加えて、複数の関数が同じ判断基準を共有すると明記した場合は、各関数のセクションの記述がその共有基準と矛盾していないかも確認する (例: 関数Aの説明に「この検証は行わない」と書いてあるのに、関数Bの説明ではその検証を行う前提のままになっていないか)。
2. **仕様レビュー**: 抽出した仕様をユーザーがレビューする。レビューを経てから次の工程に進む。想定と異なる仕様が出てきたら、実装が誤っているのか仕様抽出が誤っているのかを切り分けて修正する。
   - ユーザーに渡す前に、仕様抽出をしたものとは別のサブエージェントか新しい会話に、仕様と、それまでのレビューで出た指摘だけを渡し、本書 (testing.md) の規約に沿っているかを確認させる。指摘は、本書の条文を引用して違反と言い切れるものだけにさせる。
   - 確認は、本書の `##` 見出しの節ごとに1人のレビュアーを立て、同時に走らせる。各レビュアーには、本書の担当する節の見出しと rules/lang/<lang>.md のテスト方針の場所を示し、レビュアー自身に、担当する節とそのテスト方針の原文を、要約や省略をせず全文読ませる。
   - 1回のレビューで見る仕様が多いと確認の深さが落ちる。ファイル単位など扱いきれる単位に区切って回す。
   - 区切ってもなお1ファイルの仕様が過大になるなら、抽出の粒度でなく対象コードの責務分割を疑う。
3. **テスト生成**: レビュー済みの仕様だけを渡してテストコードを書く。実装を読んだ先入観が混ざらないよう、仕様抽出と同じ会話では行わず、サブエージェントか新しい会話で行う。仕様に書かれた種別のとおりに、結合するものと実物にするものは実物のまま、モックにするものはモックにして書く。既存テストの命名や構造を後から直す場合も同じ分離を適用する。直す理由を仕様の言葉で書き出し、実装を読んでいないサブエージェントか新しい会話に渡して書き直させる。
4. **生成物のレビュー**: テストを書いたエージェントやセッション自身に良否を判定させない。書いたものとは別のサブエージェントか新しい会話に、テストコードと、それまでのレビューで出た指摘だけを渡し、本書 (testing.md) の規約に沿っているかを確認させる。
   - 指摘は、本書の条文を引用して違反と言い切れるものだけにさせる。
   - 確認のしかたは、仕様レビューと同じにする。

## 種別の選び方

- 関数に固有のロジック (計算式・分類・変換のルールなど) があるなら、期待値を具体値で書く単体テストを作成する。
- ロジックを持たない関数には、単体テストを書かない。固有のロジックを持つ関数まで呼び出し元を遡り、部品間結合テストでカバレッジが通ればよい。
- インフラ (データベース・ドキュメントストア・キャッシュ・メッセージキューなど) に直接アクセスする実装は、ロジックの有無によらず、インフラをモックに差し替えた呼び出し元のテストだけで済ませず、インフラ結合テストを作成する。
- 生成AI (LLM など) を呼び出す実装は、出力が決定的でなく「〜のとき〜が返る」と期待値を断定できないため、スモークテスト以外のどの種別でもモックに差し替えて確認する。実際のAIへの疎通確認は、CI のスモークテストとして別に行う。
- 外部サービスなど外へ送る通信を行う実装は、そのサービスのサンドボックスを相手にしたスモークテストで確認する。サンドボックスが無いときは、テストしない。

## 大原則

- 失敗した時の処理が正しいかを確認するため、正常系だけでなく異常系のケースを作成する。
- リファクタしても壊れないテストにするため、外から観測できる結果だけをアサーションの対象にする。
  - 画面が無い場合は、以下のどちらかでアサーションする。
    - 呼び出し自体が返す結果 (戻り値・例外、応答のステータスや内容など)
    - 呼び出しのあとに別の経路から確認できる変化 (読み直した結果、他の宛先に届いたメッセージやイベントなど)
- 人間がテストの網羅性を確認しやすいように、テスト名と中身を一致させる (仕様の言葉で書く基準は「テストの命名」に従う)。
- 既存テストを別の形 (公開経路の検証など) に作り直すときは、置き換え先のテストが通ることを確認してから元のテストを消す。
  - なぜ: 先に消すと、置き換えが完成するまでその仕様が無検証になり、穴が残っても気づけないため。
- 各テストケースは、他のケースの実行順序や結果に影響されず、単独でも成立するようにする。同じ接続・DB・キューなどの状態を複数のケースで使い回すときは、ケースごとに独立した状態から始める。
  - なぜ: 他のケースの影響を受けて失敗しないようにするため。
  - テスト用のデータ作成・削除は、そのテストに関連するものだけを対象にする。
- テストコードに if 文を書かず、条件ごとに独立したテストケースとして並べる。
  - 前提 (Given) にifを使うと、どんなケースが実際に走ったか見えにくく、網羅できているか分かりづらくなる
  - アサーションにifを使うと、条件によって確かめる振る舞いが変わり、別の振る舞いの検証が混ざる。1つのテストは1つの振る舞いを確かめるべきだが、if はこれを壊す。
    ただし単体テスト以外で、後の確認が前の操作の結果に依存する一連の操作 (前の操作をしないと後の操作ができない場合) をまとめて1テストにするのはこの限りではない。
- 実データの仕様変更でテストが壊れるのを防ぐため、テストでは本番の実データ ID をそのまま使わず、テスト専用のダミー値を用いる。

## テストの命名

テスト名からテスト観点カタログを生成するため、テスト名だけを読めば仕様がわかるように命名する。

テスト関数・テストクラスには docs コメントを付与しない。テストケースの意図やシナリオも、コメント (docs コメントを含む) で説明してはいけない。コメントを書くと、仕様の記述がテスト名とコメントに分散し、テスト名だけで仕様がわかる状態が崩れる。
  - 例:「二つの集計が別々に反映されることを、値が食い違う入力で確かめる」とコメントに書く代わりに、その内容をケースの名前に書く。コメントを消すと情報が失われる。

テストの名前は、以下の順で階層化する。括弧で囲んだ段は省略できる。

`[区分:大機能(:中機能)]小機能` > (共通の前提) > (共通の操作) > 種別 > 正常異常 > ケースの名前

例：

- `[本体:注文]送料計算 > 単体テスト > 正常系 > 注文金額が3000円のとき、送料は無料になる`
- `[本体:決済:クレジットカード決済]与信判定 > 利用限度額が5万円で、注文金額が5万1円のとき > 決済を実行すると > 部品間結合テスト > 異常系 > 決済の応答は利用限度額超過を示すエラーになる`

- **区分**：以下から選ぶ。
  - **本体**：利用者や呼び出し元が目的を達成するための業務の振る舞い (例: 送料計算・会員ランク判定・注文確定・注文の保存)。
  - **運用**：システムを動かし続けるための振る舞い (例: 設定の読み込み・ヘルスチェック・ログ出力・停止処理)。
  - **外部連携**：外部サービスとの入出力 (例: 決済代行会社の応答の変換・配送業者への再送)。
- **大機能**：区分の下の機能。画面に現れる機能名や、仕様上の機能名で書く (例: 注文・会員・配送・決済)。
- **中機能**：小機能のまとまり。小機能が多すぎるときにだけ置く (例: 大機能「決済」の中機能「クレジットカード決済」「代金引換決済」)。
- **小機能**：それ以上分けない機能 (例: 送料計算・会員ランク判定・決済の実行)。関数やモジュールの単位で分かれているものは、小機能にする。コードで分かれていない値や状態の違いは、共通の前提にする。中機能と小機能を合わせて (中機能が無ければ小機能だけで)、何を検証しているかがわかるようにする。
- 区分・大機能・中機能は、コードの置き場所 (パッケージ名・ディレクトリ名・レイヤー名) ではなく、検証している機能で決める。
- **共通の前提**：複数のケースで共有する前提 (Given)。「〜のとき」の形で書く (例: 「利用限度額が5万円で、注文金額が5万1円のとき」「会員ランクが上位のとき」)。複数あるときは、共有するケースが多いものを外側にする。
- **共通の操作**：複数のケースで共有する操作 (When)。「〜すると」の形で書く (例: 「決済を実行すると」)。
- **種別**：「テストの種別」から選ぶ。単体テストにも種別を書く。
- **正常異常**：以下から選ぶ。カタログだけで正常系・異常系を見分けられるようにするため、必ず1か所置く。
  - **異常系**：前提 (Given。共通の前提を含む) に、意図した使われ方から外れた入力・状態 (呼び出し側の誤り、外部依存の失敗、ユーザーの異常操作など) が含まれるケース。結果 (Then) が呼び出し元にエラーとして返るか、正常応答として返るかは問わない。
  - **正常系**：異常系に当たらないケース。警告が表示されるだけで操作を続行できるケースは、正常系に含む。
- **ケースの名前**：そのケースのシナリオを「〜のとき、〜すると、〜になる」の一文で書く。この三つの部分を順に前提 (Given)・操作 (When)・結果 (Then) と呼ぶ。共通の前提・共通の操作に書いた前提 (Given)・操作 (When) と、それまでの階層から自明な操作 (When) は省略してよい (例の「注文金額が3000円のとき、送料は無料になる」は When を省いた形)。

- どの構文が「`[区分:大機能(:中機能)]小機能`」「共通の前提」「共通の操作」「種別」「正常異常」「ケースの名前」に当たるかは言語で異なる。rules/lang/<lang>.md に従う。
- 前提 (Given) には、値を変えると結果 (Then) が変わる前提だけを書く。
  - 例:「会員ランクが上位で、配送希望時間帯が午前、注文金額が3000円のとき、送料は無料になる」のように、送料の判定に関係のない配送希望時間帯まで書かない。注文金額が3000円で送料が無料になることだけを示せば足りる。
- 同じ前提 (Given) や操作 (When) を複数のケースが共有するときは、それをケースの名前から省き、共通の前提・共通の操作に書いてよい。
  - ケースの名前から省いた Given や When を、仕様抽出ドキュメントの冒頭の注記 (例:「特に断らない限り、操作は注文の確定」) にだけ書いてはいけない (例: 複数のケースで注文の確定を共有するなら、共通の操作を「注文を確定すると」にする)。
- Given だけが異なり Then が完全に同一な複数ケースは、テーブル駆動に統合する。
- テーブル駆動 (データ駆動) では When がテーブル全体で共有されるので、各ケースの名前は Given と Then だけにする。Given のうちテーブル全体で変化しない部分は共通の前提に書き、ケースの名前には、行ごとに変わる Given の部分と Then を書く。
  - パラメータを展開した文が日本語として読めるように書く。空文字のように見えない値は「空文字」のような言葉のラベルに置き換える。
- 複数の仕様項目で前提 (Given) の大部分を同じ文のまま繰り返し、一部の値だけを変えてはいけない。読み手が長い文を一字一句見比べないと違いが分からなくなる。
  - 例:「会員ランクが上位で、クーポンの上限が1000円のとき、注文金額が3000円で送料は無料になる」と「会員ランクが上位で、クーポンの上限が1000円のとき、注文金額が5000円で送料は無料になる」のように大半が同じ文を並べる。変わらない前提は共通の前提にまとめるか、テーブル駆動で、行ごとに変わる Given の部分と Then だけを書く。
- 前提 (Given) と結果 (Then) の値は具体値で書く。テストを実装の書き写しにしないためである。「保存した値で返る」のような抽象的な表現ではなく、「注文の配送先の郵便番号が『150-0001』で保存されているとき、取得した注文の配送先の郵便番号は『150-0001』になる」のように書く。
  - ただし、具体値がテスト専用のダミーで、検証対象が値そのものでなく境界の関係なら、「下限のとき」「上限のとき」のような相対表現でよい。
  - 実行タイミングや環境に依存して具体値が書けないもの (日時・パスなど) は、具体値の代わりにその値が何であるかを書く (例:「注文日時が 2026-09-26 03:15 になる」ではなく「注文日時が注文を確定した日時になる」)。
- リストの全要素が値の範囲内にあることを条件とするときは、範囲ではなく、下限の値の要素と上限の値の要素を両方含むリストで書く。
  - 例: カート内のすべての商品の価格が 3000 円以上 5000 円以下のとき、まとめ買いクーポンを使えるなら、「カート内の商品の価格が 3000 円から 5000 円の範囲のとき、まとめ買いクーポンを使える」ではなく、「カートに価格 3000 円の商品と価格 5000 円の商品があるとき、まとめ買いクーポンを使える」と書く。
- ケースの名前など自由文で書ける箇所は日本語の仕様の言葉で書く。語の選び方 (英語の一般語を地の文に混ぜない等) は documentation.md に従う。
  - ただし、利用者が画面・API・保存形式・設定でそのまま見る/触る名前・値は、日本語に言い換えずそのまま使う (例: キー名、列挙値、NaN のような特殊値、HTTP ステータスコード、環境変数名、画面の実文言、JSON・UTC のような定着した略語)。
- 外部を読み書きするコード (リポジトリ・アダプタなど) のテストは、そのコードの操作の言葉 (保存する・取得する・変換するなど) で書いてよい。ただし、確かめている性質が利用者にも見えるもの (表示のされ方・許可されるかどうかなど) なら、利用者の言葉で書く。
- 仕様の言葉で名付けられないときは、名前の付け方ではなく設計を疑う。実在しない言葉を発明して取り繕わず、公開された入口を通さず内部の変換や伝搬だけを検証していないか (「アンチパターン」の変換関数直接テストなど) を確認する。
- テスト名に実装の言葉を含めてはいけない。実装の言葉とは、仕様の利用者が使わず、実装を読んで初めて出てくる語であり、変数名・関数名のような識別子に限らず、引数・戻り値のようにプログラムの構造を指す語も含む。
  - 例: ケースの名前に `shippingFee` や `calcShippingFee()` のような変数名・関数名をそのまま使ってはいけない。仕様の言葉に言い換えられておらず、実装を読まないと意味がわからない。
  - 小機能も同様で、テストする関数の名前をそのまま使ったり、括弧で添えたりしない (×「送料計算 (calcShippingFee)」)。テストする関数はファイルの場所から特定できる。
- テスト名は、`[区分:大機能(:中機能)]小機能` からケースの名前までを繋げた全体で、前提 (Given)・操作 (When)・結果 (Then) が読み取れるようにする。
  - 例:「上位ランクになる」のように、どの累計ポイントのときの話か読めない名前にしない。「累計ポイントが 10000 pt 以上のとき、上位ランクになる」のように前提から書く。定数や不変条件を確かめるテストのように、前提が対象そのものに含まれる場合はこの限りではない。
- 結果 (Then) に観測点の無い動詞を使ってはいけない。
  - 例:「上位ランクの特典が反映される」だけでは、どこで確認できるかが分からない。「会員ランクを上位にすると、注文確認画面に送料無料の表示が出る」のように、結果をどこで観測できるか (どの画面・応答・取得結果) まで書く。
- エラーを返すケースの結果 (Then) は、エラーの原因を利用者の言葉で書く。
  - 例: 「在庫が無い商品を注文したとき、注文の応答は在庫切れを示すエラーになる」。
- テストが注入したダミー値を、本番の仕様値であるかのように名前へ書いてはいけない。
  - 例: テストでは閾値を 1000 pt に差し替えているのに、「累計ポイントが 1000 pt 以上のとき、上位ランクになる」と書くと、読者は 1000 pt を仕様の閾値 (実際は 10000 pt) だと誤認する。仕様値でないなら「設定した閾値以上のとき、上位ランクになる」のように相対表現で書く。
- テスト名や括弧の注記に実現方法 (How) を書いてはいけない。
  - 例: 「送料計算 (合計金額 × 0.1 で算出)」のように計算式を注記したり、「複数の候補があるとき、抽選で1件選ばれる (乱数を固定した先頭要素)」のようにテストで固定した乱数や内部の手順を注記したりしない。前提 (Given) と結果 (Then) だけを書けば十分で、実現方法は実装を読めば分かる。
- テスト観点カタログは、この階層のとおりに見出しの入れ子を作る。

## ロジックのテスト

ロジックを確かめるテストに適用する。

- 条件によって扱いが変わる境界ごとに、その境界で隣り合う二つの値だけを、境界値のケースにする (例: 整数で、注文金額が3000円以上なら2999円と3000円、3000円以上5000円以下なら2999円と3000円、5000円と5001円)。
- 件数や有無で扱いが変わるなら、0 件・1 件・複数件、「無い」と「空」をケースに分ける。

## 入口と結果の確認

単体テストとスモークテスト以外のテストに適用する。

- 途中の状態を手で用意して割り込ませず、公開された入口 (API・画面操作など)から実行する。
  - なぜ: 途中から始めると、入口から結果までの経路が壊れていても気づけないため。
- 操作した結果まで確かめる。「例外が出ない」「エラーが無い」「件数が合う」だけで終えず、操作の後に実際にどうなったか (保存された内容・返ってきた値・変化した状態) まで踏み込む。
- 二重送信の防止は、同じ操作を 2 回続けて行い、保存された内容が 1 件だけであることを確かめる。

## 異常系からの回復

単体テストとスモークテスト以外のテストに適用する。

- 異常系の確認は失敗した状態を見るだけで終えず、そこからの回復まで確認する。再試行 (または次の正常な操作) をすると成功すること、失敗時に出た状態 (エラー表示など) がその後の操作まで残り続けないことを確かめる。
  - なぜ: 失敗時の表示や状態を出しっぱなしにする不具合は、失敗した瞬間だけを確認するテストでは検知できないため。
  - 回復の確認は、失敗後の状態が同じ異常系の間では繰り返さず、その状態ごとに一つ確かめる。失敗後の状態とは、失敗の直後に利用者や呼び出し元から観測できる表示・保存内容・次に取れる操作を指す。
    - なぜ: 経路が異なる異常系でも、失敗後の状態が同じなら回復の振る舞いは変わらないため。

## 接続先が使えない環境での失敗

単体テスト以外のテストに適用する。

- 接続先 (エミュレータ・DB コンテナ・別のサービスなど) が使えない環境では、テストを沈黙スキップせず失敗させる。
  - なぜ: スキップが常態化すると、検証されていないのに全体が通ったように見えるため。

## E2Eテストとシナリオテストの実行環境

- E2Eテストとシナリオテストは、テスト専用の環境で実行する。

## シナリオテスト

- シナリオテストは、利用者が目的を達成するまでの一連の操作 (動線) を最初から最後まで確かめる。
  - なぜ: 部品間結合テストやサービス間結合テストが通っていても、全体を動かしたときに利用者が目的を達成できるかは確かめられないため。
- 動線の種類は次のとおり。
  - **通常の動線**：会員登録・ログイン・商品の閲覧・カートへの追加・決済を最後まで通す。
  - **異常から回復して目的を達成する動線**：決済に失敗したあと、再試行して注文を確定する。
  - **最終的にエラーになる動線**：在庫が無い商品を注文し、注文できないエラーが表示される。
  - **利用者設定を挟む動線**：配送先を変更してから注文を確定する。
- シナリオテストの名前は、「テストの命名」の区分・大機能・小機能の規定の例外とする。区分は「本体」、大機能は動線の始点と終点 (例: `[本体:会員登録から購入]`)、小機能は動線の種類 (上の4つ) にする。

## スモークテスト

- スモークテストは CI で実行する。

## GUI (画面) のテスト

画面を持つアプリのテストに適用する。

- 画面に見える結果で判断する。画面の切り替わり・表示内容・エラー表示を確かめる。画面を組み立てる内部の部品への呼び出しや内部の値は検証しない。
- 部品間結合テストでモックにするのは外部との境界だけ。通信・WebSocket・ログインなどを代用に差し替え、画面を組み立てる内部の部品は実物を使う。
  - なぜ: 部品どうしの連携が壊れていても気づけるようにするため。
- API 通信のモックは HTTP 境界 (ネットワーク層) で行う。api クライアント / モジュールを直接差し替えない。
  - なぜ: api モジュールを差し替えるとリクエスト組み立て〜レスポンス処理の経路が飛ばされる。ネットワーク層でモックすれば実際の通信経路を通して検証できるため。
- 見た目や実装の詳細に依存させない。CSS クラス名・アニメーションの文字列・配置の係数・固定の待ち時間などを確かめの対象にしない。
  - なぜ: 見た目を変えただけで壊れ、ユーザーに見える動きを確かめていないため。
- 要素を探す・確かめるときは、画面に見えるテキストや role を優先する。テキストや role が同じまま裏側の状態だけ変わる場合など、見た目だけでは区別できないときに限り、role / aria-* / data-state のような意味を持つ属性で確かめる。data-testid のような実装専用の識別子は、それでも区別できないときの最終手段とする。
  - なぜ: テキストや role は画面に見える情報でユーザー体験と直結するが、data-testid は画面に現れず、コンポーネントの実装が変わっただけでテストが壊れる。
- 操作は実際のユーザー操作として発火させる。内部のイベントハンドラを直接呼ばない。
- 二重送信の防止は、同じ操作を 2 回続けて行い、1 回目の後に再度の操作ができない状態 (例: ボタンが無効になる・処理中の表示が出る) になること、または 2 回の操作の後に画面へ表示される結果が 1 つだけであること (例: 注文一覧に 1 件だけ表示される) を確かめる。
- 応答が届く順序で結果が変わる振る舞い (例: 商品一覧の絞り込みを切り替えたとき、遅れて届いた前の絞り込みの応答で一覧が上書きされない) は、境界のモックの応答を返すタイミングをテストが制御し、先に送った要求への応答を後から返して確かめる。
  - なぜ: 固定時間の遅延で応答を遅らせると、待ち時間より先にアサーションが終わった場合に、遅れた応答が届く前に判定してしまい、上書きの不具合を検知できないため。

## アンチパターン

- テストは、ビルドが通ることだけで完了としてはいけない。
  - 例: ビルドが通ることを確認しただけで、テストを実行して確かめたことにする。ビルドが通ることは構文や型が合っていることを示すだけで、クエリや外部呼び出しが正しく動くかどうかは確認できていない。
- 入力と出力の対応を、変換関数を直接呼んで突き合わせてはいけない。
  - 例: エラー→HTTP ステータスの変換関数を単体で呼び、対応を 1 件ずつ確かめる。コードの分岐を書き写しただけで、その状況で本当にその出力が返るかは確かめていない。
  - 除外: 契約の SSoT が、実際の通信を介してこの変換を確かめている場合。
- 生成物の文字列を期待文字列とそのまま突き合わせてはいけない。
  - 例: 生成した SQL やコードを文字列比較で確かめる。書式を変えただけで壊れやすく、実行した結果が正しいかは確かめていない。
  - 完全一致を部分一致に緩めても、実行した結果を確かめていない点は変わらない。生成物を実行し、その結果 (更新された行・出力された内容) を確かめる。
- 依存を欠けた状態で渡し、早期エラーだけを確かめてはいけない。
  - 例: ハンドラに依存を欠けた状態(nil/null/未設定など) で渡し、入力エラーの 400 や「落ちない」ことだけを確かめる。本来の処理(依存を呼んで結果を返す) に届かず、配線の欠落を見逃す。
- モックが「呼ばれたこと」「呼ばれた回数」だけを確かめて終えてはいけない。
  - 例: 配信関数が 1 回呼ばれたことだけを確かめる。誤った内容が渡っていても緑のままになる。操作の後に実際に起きた結果 (保存・配信された内容) まで確かめる。
- 異常系で、失敗した (エラーになった・例外が飛んだ) ことだけを確かめて終えてはいけない。
  - 例: 認証ヘッダが無い場合とトークンが無効な場合のように、原因が異なるのに同じステータスコードや同じ例外型になる分岐がある。両方のテストがステータスコード・例外の型だけを確かめていると、片方の分岐が誤ってもう片方の理由を返しても検知できない。返ってきたエラーメッセージや種類など、原因を区別できる内容まで確かめる。
  - メッセージを指定しない `toThrow()` も同様の弱さを持つ。別の原因のエラーが飛んでも通ってしまうため、想定した原因のエラーであることまで確かめる。
- 結果が存在することだけを確かめて終えてはいけない。
  - 例: 注文確認メールの本文が空でないことだけを確かめる。本文が別の注文のものでも緑のままになる。本文に含まれる注文番号など、期待する内容まで確かめる。
- 同じプロセス内の部品に渡された引数を確かめてはいけない。
  - 例: 送料計算が会員ランク判定に会員 ID をそのまま渡したことを、差し替えた判定が受け取った引数から確かめる。引数は外から観測できず、リファクタで壊れる。送料など外から観測できる結果で確かめる。
- 不具合修正のあとに追加するテストは、直した不具合の再発だけをピンポイントで確かめてはいけない。
  - 例: 「送料が負の値にならない」のように、修正前に起きていた症状が出ないことだけを確かめる。同じ処理に潜む別の不具合には反応せず、本来の仕様に沿った期待値 (例: 「送料は 500 円になる」) を確かめれば、直したバグも含めて仕様から外れる結果を検出できる。
- 期待値をアサートした上に、その裏返しの「起こらないこと」を重ねて確かめてはいけない。
  - 例: 送料が 500 円であることを確かめた上で、さらに送料が -1 円でないことも確かめる。期待値のアサーションが通れば否定は自動的に成り立ち、何も確かめを足していない。
- 実装をテストに書き写してはいけない。
  - 例: フィールドのコピーや定数をそのまま写す、期待値をテストするコードと同じ計算で作る。実装とテストが二重管理になり、両方に同じバグが入れば気づけない。
  - 本番コードの定数や関数を取り込んで期待値を組み立てるのも同じ書き写しであり、定義が誤っていても両側が同時に変わり検出できない。期待値はテスト側のリテラルで書く。
  - 除外: 純粋な関数 (計算式・分類・命名規則) を具体値で直接確かめる場合。
- モックに対するスモークテストを作ってはいけない。
  - 例: 決済代行会社の API に本当に接続できるかを確かめるスモークテストを、モックサーバーに向けて実行する。実物に接続できるかは何も確かめていない。
- 本番に無い検証ロジックをテスト内で作って確かめてはいけない。
  - 例: 本番に存在しないロジックや変換をテスト内に書き、自前の入力に当てる。テスト内で完結し、本番コードを何も通っていない。
- モック自体の動作を確かめてはいけない。
  - 例: 決済代行会社のモックサーバーが、受け取った金額をそのまま返すことを確かめる。本番のコードを何も通っておらず、モックが実物とずれても検知できない。
- テストするコードでないライブラリそのものの挙動を確かめてはいけない。ライブラリの品質はライブラリ開発者の責任であり、このプロジェクトで検証しても仕方がない。
