# コーディング規約

Key and Notes 各プロジェクト共通のコーディング規約。コードを書くときに従う。

## 設計思想

- エラーは握りつぶさず根本解決する。ログだけして握りつぶすのは禁止
- 保守性を高めるため、原則としてエラー回避のためのワークアラウンドを書かない
- 想定外の入力・状態 (未知の種別・分類できない値など) は異常系として扱う。正常系の一種として黙って通さない
- デフォルト値へのフォールバックを行わない。意図しない値になるならエラーにする
- 一つの関数に複数の責務を負わせない。二つの操作を並べないと関数の振る舞いを名前で表せない (例: `validateAndSave`) なら、責務が複数あるので関数を分ける。操作を一つだけ書いた名前や、`process`・`handle` のような広い意味の名前に変えて済ませてはいけない
- ロジックは単純なほど読みやすく保守しやすいため、要件を実現する処理はできるだけ単純にする
  - 要件とルールが求めることだけを実装する。どの要件・ルールを満たすためにあるか示せない処理 (例: 分岐・状態・データの種類・設定の切り替え) を足さない。要件が明示していない処理が必要だと考えたら、実装する前にユーザーに確認する (例: 要件が会員ランクごとの送料を定めていないなら、ランクで送料の計算を分けない)
  - 同じ要件を満たす書き方が複数あるなら、分岐・状態・データの種類が少ないほうを選ぶ
- 新しいコードが既存コードと同じ概念を表し、片方の変更がもう片方にも及ぶ関係にあるなら、部品として切り出して共通化する
- 共通化に既存コードの修正が要る場合も、修正を避けない。既存コードに触れないことを理由に、共通化すべき部分を重複させたまま実装しない
- 生成済みコードを手で書き換えない。型・スキーマ・定数等は SSoT を変更してから生成スクリプトを再実行する（該当する SSoT がある場合に適用）
- 業務ロジックは DB・外部 API・フレームワーク・乱数・時刻など、外部の具体的な実装に直接依存しない。ロジック側でインターフェースを定義し、具体的な実装はそのインターフェースを実装する側に置く。
  - 外部の変更がロジックに波及せず、実装を差し替えられるようになる
  - テストで本物と偽物を差し替えられ、テストのしやすさが向上する
- 外部とのデータの変換は、外部と直接やり取りするコード (外部を読み書きする処理と、外部からの呼び出しを受ける処理) に置く
  - 外部から受け取ったデータは、そこで業務ロジック側の型に変換してから渡す。型が決まっていない値のまま渡さない
  - 外部に渡すデータは、業務ロジック側の型のまま渡し、外部の形式への変換はそこで行う

## コーディング方針

- マジックナンバーを使用しない。定数化し、数値の用途がわかるようにする
- コメントは原則書かない。書いてよいのは、関数・クラス・型に付与する docs コメントと、実装から読み取れない意図を示す Why コメントの二種類のみ
- コメントで説明したくなったら、先に実装・設計・前提を疑う。テスト名が仕様の言葉で名付けられないとき、命名でなく設計を疑う (testing.md) のと同じ手順である
  - 出典を示せない正当化 (「暗黙の仕様」「従来通り」「念のため」等) は Why ではなく作話であり、書く前に前提を検証する
  - 説明が長くなる箇所は、コメントで補う前に責務を分割できないか検討する
- モジュール外部から参照される (公開の) 関数・クラス・型には docs コメントを付与する。非公開の関数・クラス・型に付与するかは任意
  - 言語ごとの docs コメント形式は rules/lang/<lang>.md が定めるが、付与対象 (公開は必須・非公開は任意) は本規約に従う
  - 要約のみを書く。実装手順や設計判断の列挙はしない
  - 設計上のトレードオフによる Why は ADR に、仕様・業務ルールとしての Why は BDR に、行レベルの Why はその行のインラインコメントに分離する
  - 実装の言葉ではなく仕様の言葉で書く
- 実装との二重管理になるので What コメントを書いてはいけない
  - Why がかかる先を示すために、処理内容を要約の粒度で添えるのは可
  - 機能や画面要素を削除した後に「〜はしない」「〜は表示しない」と否定形の説明を残さない。動作しないことは現在のコードから読み取れるので、Why のない否定の記述はノイズになる。ドキュメントでも同じで、あえて対象外にしたことを書くなら理由 (why) を添える
- 実装から読み取れない意図は Why コメントとして記述する。設計上のトレードオフなら ADR に、仕様・業務ルールとしての判断なら BDR に記述する
  - 変更の歴史的経緯（以前はこうだった／いつ何をなぜ変えた）は Why ではない。現在のコードを読むのに不要なので、コメントに書かず、残すなら ADR・BDR や git 履歴に置く
  - 特に ADR・BDR 番号の参照（「ADR-xxx に基づく」等）をコメントに書かない。ADR・BDR の内容が Why なら本文に直接書く
  - Why コメントは「〜のため、〜する」の一文で書く。理由を一つに絞れない、または代替案の比較や却下理由に触れる場合は行レベルの Why ではなく設計上のトレードオフであり、ADR に書く
- アプリ間の契約 (エンドポイント・イベント名・ヘッダ名) はリテラルで書かず、所有サービスが発行する API 契約パッケージを参照する
- TODO を残すときは Issue を立ててリンクする。Issue へのリンクが無い TODO をコミットに残さない
- 関数名は動詞から始め、何をする関数かを明確にすること
- 今使わないコードは残さない (動線があってもロジック的に呼ばれないコードを含む)
- 実装を変更したら関連 docs を同期する (ただし過去の ADR・BDR は変更しない)

## 命名規約

命名規約は、名前を付けるものすべてに適用する。

- 関数・メソッドは名前から振る舞いが読み取れるようにする (原則として動詞で始める)
- 真偽を表す関数・変数は、真偽が読み取れる接頭辞を付ける (is / has / can / should 等)
- 一般的でない略語を使わない (ドメインで定着した語・各言語の確立した短縮語は可)
- 同じ概念には常に同じ語を使う。新しい名前を付ける前に、仕様書・既存コード・ドキュメントで同じ概念を指す語が既に使われていないか確認し、あればそれに揃える
- ドメインの概念を表す語は用語集に従う
- 名前は、それが何であるかで決める。それを扱う技術や通信の形式では決めない。ただし、技術そのものがその実装の正体である場合 (例: PostgreSQL に特化した実装クラス名は `PostgresOrderRepository` にする) は例外とする
- ドメインの概念を表さない名前 (例: ファイル・ディレクトリ・クラス・関数・変数・起動オプション・保存するデータのキー) は、本規約に従って Claude が決め、個別にユーザーの確認を求めない。本規約で決められない場合のみユーザーに確認する
- Claude が造語や、仕組みを別のものにたとえた言い方 (例: よく一緒に購入される商品を自動でまとめる処理を「福袋ロジック」と呼ぶ) で勝手に名付けない
- 既にある語と条件の組み合わせで書ける状態に、語を作らない。条件はそのまま書く
- リポジトリ内で対象が一つに定まらない動詞だけで名前を作らない。何に対する操作かを名前に含める
- 同じ並び (同じフォルダの下、同じコマンド群) の名前は、モノの名前か操作の名前かをそろえる
- 上記の具体化と言語固有の命名慣用は rules/lang/<lang>.md に従う。rules/lang/<lang>.md にない命名は、言語・フレームワークの公式スタイルガイドに従う
- テスト名の詳細な指針は testing.md に従う

## ログ方針

- 構造化されたログを出力する
- ログ出力すべき事象
  - 呼び出し元に伝搬させられないエラーの補足
  - エラーではないが、その場所でしか気づけない事象 (未対応のイベント種別など)
- ログレベル
  - `Info`: 起動・停止・正常系の事象
  - `Warn`: システムの運用に影響を与えない、あるいは影響が軽微な事象
  - `Error`: システムの運用に支障をきたす事象
