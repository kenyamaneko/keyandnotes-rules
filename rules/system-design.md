# システム設計

システムを設計するときに従う規約。

## SOLID 原則

保守性と拡張性を高めるため、SOLID 原則に従う

- **単一責任**：関数・クラス・モジュールは、それぞれ責務を一つだけ持つ。責務が一つとは、変更される理由が一つだけであることを指す (例: 送料計算を変更するのは、送料の計算ルールが変わるときだけにする)
  - 二つの操作を並べないと名前で振る舞いを表せない (例: `validateAndSave`) なら、責務が複数あるので分ける。
  - 操作を一つだけ書いた名前や、`process`・`handle` のような広い意味の名前に変えて済ませてはいけない
- **開放閉鎖**：要件が複数の種類を定め、種類ごとに振る舞いが違うときは (例: 配送業者ごとに送料の計算が違う)、種類ごとの実装を同じインターフェースの実装として並べ、新しい種類を実装の追加だけで足せるようにする
- **リスコフの置換**：インターフェースの実装は、どの実装に差し替えても、使う側のコードを変えずに動くようにする
- **インターフェース分離**：インターフェースには、それを使う部品が必要とする操作だけを定義する
- **依存性逆転**：業務ロジックは DB・外部 API・フレームワーク・乱数・時刻など、外部の具体的な実装に直接依存しない。業務ロジックが必要とする外部の機能は `port` にインターフェースとして定義し、具体的な実装は `adapter` に置く。
  - 外部の変更がロジックに波及せず、実装を差し替えられるようになる
  - テストで本物と偽物を差し替えられ、テストのしやすさが向上する

## クリーンアーキテクチャと役割の名前

保守性と拡張性を高めるため、クリーンアーキテクチャに従う

- 実装を置く場所の直下のディレクトリ・パッケージ・プロジェクトは、すべてアーキテクチャ上の役割で分ける。実装を置く場所は、言語別のルールに書く
- 全言語に共通の層と名前は次の表のとおり。使わないものは作らなくてよい。表記は言語の慣用に合わせる

  | 層の名前 | 役割 | 業務ロジックを持つ |
  |---|---|---|
  | `domain` | 業務ロジックと型 | ○ |
  | `usecase` | 複数の処理をつなぐ業務の操作 | ○ |
  | `port` | 業務ロジックが外部の機能を使うために定義するインターフェース | × |
  | `adapter` | データベースや外部サービスなど、外部との接続 | × |
  | `presentation` | 外部からの呼び出しの受付 (例: REST、ワーカー) | × |
  | `config` | 環境変数などの設定の読み込み | × |
  | `main` | アプリの入口。起動と、部品の生成・接続 | × |

以下の図は層の依存関係を表す

  ```mermaid
  flowchart TB
    main["main"]
    presentation["presentation"]
    usecase["usecase"]
    port["port"]
    adapter["adapter"]
    domain["domain"]
    config["config"]
    main --> presentation
    main --> usecase
    main --> adapter
    main --> config
    presentation --> usecase
    presentation --> domain
    usecase --> domain
    usecase --> port
    port --> domain
    adapter --> port
    adapter --> domain
  ```

  - `usecase` は `adapter` を直接使わず、`port` のインターフェース越しに使う
  - `main` が `adapter` に依存するのは、`adapter` を生成して `usecase` に渡すためである
  - `main` が `config` に依存するのは、設定を読み込んで `adapter` などに渡すためである
  - 業務ロジックを持たない層が `domain` を使うのは、型を受け取る・返すためだけにする

## 共通化

- 新しいコードが既存コードと同じ概念を表し、片方の変更がもう片方にも及ぶ関係にあるなら、部品として切り出して共通化する
- 共通化に既存コードの修正が要る場合は、既存コードを修正して共通化する

## 外部とのデータ変換

- 外部の形式のデータ (例: データベースの行、外部 API の応答、リクエスト本文) と、業務ロジック側の型との変換は、`adapter` と `presentation` で行う
  - `adapter` と `presentation` は、外部から受け取ったデータを業務ロジック側の型に変換してから、`usecase` や `domain` に渡す (例: 注文を受け付ける `presentation` は、リクエスト本文を業務ロジック側の注文の型に変換してから、`usecase` に渡す)
  - `usecase` や `domain` は、外部に渡すデータを業務ロジック側の型のまま `adapter` や `presentation` に渡し、外部の形式への変換はそこで行う (例: 注文を保存する `adapter` は、業務ロジック側の注文の型を受け取り、データベースの行に変換して保存する)
- `adapter` は、接続先ではない外部の型を使わない (例: データベースに注文を保存する `adapter` は、注文 API の応答の型を使わない)

## データの編集

- 業務データを保持するデータソース (テーブル・文書・ファイル) への編集 (作成・更新・削除) は、一つの機能だけが行う。読み取りは複数の機能が行ってよい
  - なぜ: 競合を避けるため、データの更新は一つの機能だけの責務にする
- 複数の機能が同じ情報を更新したいときは、編集する機能を一つに決めて他の機能はその機能に依頼するか、編集する機能ごとにデータソースを分ける (例: 注文機能と入荷機能が在庫数を増減させたいなら、在庫機能だけが在庫数を編集し、注文機能と入荷機能は在庫機能に引当・入荷を依頼する)
- 各サービスが所有するマスターデータは、そのサービスだけが編集する (そのサービスが唯一の SSoT)。他のサービスは、データベースを直接読み書きせず、所有するサービスの API 経由でアクセスする (例: 注文サービスは、会員サービスが所有する会員情報を、会員サービスの API 経由で読み取る)

## エラーの伝搬

- エラーは、対処できる層まで呼び出し元へ伝搬させる
  - なぜ: エラー処理を簡潔にし、責務を分離して保守性を高めるため
- 途中の層でエラーに手を加えてよいのは次の目的に限る。いずれも、再試行で回復した場合を除き必ず伝搬させる
  - 再試行のため
  - エラーを業務ロジック側の型に変換する・文脈を付加するため (変換・付加のうえ改めて呼び出し元へ伝える)
  - リソースの後始末のため (後始末のうえ改めて呼び出し元へ伝える)

## 不変性

- ドメインの値 (例: 注文金額・会員ランク) は、更新のたびに元の値を書き換えず、変更後の新しい値を返す
