# データ設計

RDB・ドキュメントストアのデータを設計するときに従う規約。

## RDB とドキュメントストアに共通の規約

### 金額

- 金額は、誤差の出ない整数か固定小数点数で持つ

### 日時

- 日時は UTC で持つ。タイムゾーンへの変換は、表示するときに行う

### 削除

- データの削除は、削除日時を使って論理削除にする

## RDB

### 主キー

- 主キーは、基本は UUIDv7 にする
  - なぜ: UUIDv7 は時刻順に並ぶため、UUIDv4 のようにランダムな位置へ挿入されず、索引が断片化しにくい
- ユーザー ID や取引 ID のように、ID に含まれる作成時刻から事業の規模を推測されると困るものは、作成時刻を含まない UUIDv4 にする
- 他のテーブルの主キーと連番などの組み合わせで一意に決まるテーブルは、その組み合わせを主キーにする
  - 例: 注文明細は、注文 ID と行番号の組み合わせを主キーにする

### NULL

- NULL は、対象となる値そのものが存在しないときだけ使う。false や「未回答」「結果不明」などで表せるなら、NULLにしてはいけない
  - 例: 会員の退会日時は、退会していない会員には退会日時という値が存在しないので、NULL にする
  - 例: 会員のメールマガジン購読は、購読しないと答えた場合も、まだ答えていない場合も、状態として表せるので、NULL にせず「購読しない」「未回答」とする

### 正規化

- テーブルは第三正規形まで正規化する
- 第三正規形より前の正規形にするのは、パフォーマンスの問題があり、ユーザーが認めた場合だけにする

## ドキュメントストア

### 構造の決め方

- ドキュメントは、画面や API の応答が一度に使うデータの単位で作る

### 入れ子

- 画面や API の応答が一度に使うデータは、元のドキュメントの中に入れ子にして持つ
  - ただし、ドキュメントの大きさの上限を超えないようにするため、件数が際限なく増えるものは除く
  - 例: 注文の詳細画面で注文と注文明細を一度に表示するなら、注文明細は注文のドキュメントの中に入れ子にして持つ

### 整合性

- 食い違ってはいけないデータは、同じドキュメントに入れる
  - 例: 注文のステータスと発送日時は同じドキュメントに入れる
